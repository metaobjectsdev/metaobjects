# ADR-0044: Payload-record naming under a cross-package short-name collision

## Status

**Accepted** (2026-07-20). Fixes #219 (C#), closes #220 (the Java/Kotlin collision-conformance gap). Extends [ADR-0041](ADR-0041-cross-package-reference-resolution.md) / [ADR-0042](ADR-0042-bare-references-are-package-local.md) (FQN-exact, package-local reference resolution) from the *metadata resolution* tier to the *codegen emission/naming* tier. Stage 1 (this decision + the TS reference fix + the C# fix) ships now; the Java/Kotlin/Python follow-up is tracked separately.

## Context

A generated **payload record/type/interface** (the typed shape a `template.output`/`template.prompt`'s `@payloadRef` binds to, and every nested `field.object @objectRef` it reaches) is named after its value-object's bare short name in every port — `Note`, `Digest`, `AuthorBrief`. ADR-0041/0042 made a specific, deliberate metamodel move: a `field.object @objectRef` may be **fully-qualified** (`acme::alpha::Note`), so two *different* packages can each declare an `object.value` with the *same* short name, and a third object can reference **both** by FQN. This is valid, loader-accepted metadata — the cross-package short-name collision corpus (`fixtures/template-output-render-conformance/xpkg-collision/`) exists specifically to exercise it: `acme::alpha::Note { alphaText }` and `acme::beta::Note { betaText }`, both referenced by `acme::app::Digest`.

No port's payload-record emitter was designed for this. An audit across all five ports found the metadata **resolves** correctly everywhere (TS/Java/Kotlin/Python; C# additionally mis-resolves — see #219), but **naming/emission** breaks in three distinct ways, none of them a loud failure:

1. **Bare-keyed dedupe drop (TS, and C# once its resolution bug is fixed).** The emitter dedupes the interfaces/records it has already emitted by the value-object's *bare* name. The second `Note` is treated as "already emitted" and silently dropped; both `Digest.fromAlpha` and `Digest.fromBeta` end up typed against `acme::alpha::Note`'s shape. A field that only exists on the beta shape (`betaText`) type-checks as present on data that never carries it.
2. **File clobber (Java, Kotlin).** FQN-keyed dedupe correctly emits *two* record declarations — but both are named `NotePayload` and written to the same file path in the same output package. The second write silently overwrites the first; every reference in the file resolves to whichever one survived.
3. **Wrong-node resolution (C#, pre-fix).** The nested `@objectRef` is stripped to its bare short name *before* resolution, so the FQN distinction is lost even before dedup runs — `FindObject` matches whichever same-named object.value it enumerates first, in either package.

Every one of these produces a program that **compiles and runs**, silently binding the wrong shape. This is worse than a load error: ADR-0023's fail-closed discipline and the repo's "a gate that reports green while wrong is worse than no gate" precedent (#224/#225) both apply directly. The corpus's own README had, until now, punted on this: "each port's runner hand-authors — or otherwise reconciles — the payload record… naming is an orthogonal concern this sub-corpus does not settle." That punt is what this ADR closes.

## Decision

**One distinct emitted type per resolved value-object FQN**, package-qualified only where collision demands it:

1. **Resolution stays FQN-exact / package-local (ADR-0041/0042), unchanged.** This ADR does not touch *how* a `@objectRef` resolves — only how the resolved node is *named* and *deduplicated* for emission.
2. **Dedup key is the resolved node's FQN (`resolutionKey()`), never its bare name.** A closure walk over a payload root's transitive `@objectRef` graph collects every reachable value-object keyed by FQN before any name is decided.
3. **Naming is a two-tier, closure-scoped rule, applied once per emitted artifact:**
   - The **closure** (collision domain) is the transitive `@objectRef` graph of the payload root(s) emitted together into one artifact — the emitted **file** for a single-file emitter (TS `payloads.ts`, C# `<Payload>.payload.cs`, Python `<template>_payload.py`), the **output package for the run** for a one-class-per-file emitter (Java, Kotlin). It is the *referenced-only* closure: an unrelated same-named value-object elsewhere in the loaded tree that this artifact never reaches does not force qualification.
   - A value-object whose bare short name is **unique** within that closure emits under its bare short name, run through the port's existing naming convention (`Note` in TS/C#; `NotePayload` in Java/Kotlin/Python) — **byte-identical to today's output**.
   - A value-object whose bare short name **collides** with another closure member: **every** member of that collision set — not just the second one encountered — emits under a **package-qualified derived name**: PascalCase each `::`-segment of the resolved node's effective package, concatenate, append the bare short name, then apply the port's convention (`acme::alpha::Note` → `AcmeAlphaNote` in TS/C#, `AcmeAlphaNotePayload` in Java/Kotlin/Python). The declaration, the file/module name (for one-type-per-file emitters), and *every reference* to that type use the same derived name.
   - Naming is a **pure function of the closure** — the (FQN, bare name, package) triples reachable from the root(s) — never of walk/traversal order. Two runs over the same metadata, or a different field-visitation order, produce the identical name assignment.
4. **Backstop: if two distinct FQNs still derive the same name after package-qualification** (pathological — e.g. `acme::alpha::Note` and `acmeAlpha::Note` both PascalCase-fold to `AcmeAlphaNote`), generation **fails loud** with a dedicated error rather than silently colliding a second time: `ERR_PAYLOAD_NAME_COLLISION` — *"payload record name collision: `"<DerivedName>"` derives from both `"<fqnA>"` and `"<fqnB>"` — rename one value-object or move it to a package that derives a distinct name."* This is a **codegen-time generator error**, not a loader error (the metadata that reaches it is valid; the *emission* cannot proceed) — the same category as `ERR_VAR_NOT_ON_PAYLOAD` (FR-004's build-time drift gate).
5. **Not breaking.** No currently-*correct* output changes — only output that is silently wrong today (dropped fields, clobbered files, wrong-package bindings) changes shape. Ships as a coordinated bug-fix release, not a metamodel change (ADR-0023 is unaffected: no new vocabulary, this is purely a codegen naming/dedup contract).
6. **Accepted instability, stated honestly.** Adding a second same-short-name reference into a closure that was previously collision-free renames the first (previously-bare) type to its qualified form. This is deterministic and compile-visible — the build breaks at the now-renamed reference, not at runtime — and is handled by ordinary regen + (where the port has it) three-way merge. The alternative — *always* qualifying every payload type regardless of collision — was rejected (see below): it breaks the common (non-colliding) case for every existing consumer, for a benefit only the rare colliding case needs.

### Why not the alternatives

- **Language-native namespacing** (nest the record inside its package's own namespace/module instead of renaming it) is not a uniform, implementable rule across the five ports. TypeScript has no usable in-file namespace for this (the `namespace` keyword is legacy; real module scoping means one file per value-object — a wholesale file-layout change). Python's payload modules are deliberately single, self-contained files per template (the generator's own module docstring documents this as intentional — cross-file dedup is a footgun it was designed to avoid). Making this work in C#/TS/Python means restructuring output layout per-VO-per-file; in Java/Kotlin it means moving nested payload records out of the template's `<pkg>.prompts` output package into per-VO packages — an import-path break for **every existing consumer**, non-colliding or not. Rejected because it breaks the common case that qualification-on-collision leaves untouched, for zero additional correctness.
- **Fail loud unconditionally on any cross-package short-name collision** (never attempt qualification) was rejected because the metadata is *valid*. ADR-0041/0042 exist precisely so a payload can reference two same-named value-objects across packages by FQN — the `xpkg-collision` corpus fixture is exactly this, authored on purpose. Refusing to generate valid, unambiguous metadata would make that part of the reference-resolution vocabulary a dead letter. Fail-loud survives only as the **backstop** (decision §4), for the case qualification genuinely cannot disambiguate.
- **A merged/union record** (one type carrying both `Note` shapes' fields, all optional) was rejected as the same silently-wrong-adjacent compromise the corpus's own test scaffolding had resorted to as a workaround. It is a **third shape that exists in no metadata**: both sides' fields go optional, which erases `@required` (both corpus fields are declared `@required: true`) — and a field-name typo checked against the *wrong* one of the two real shapes still type-checks against the merged one. It is precisely the shape the corpus README flagged as "an orthogonal concern" the tests had not actually settled.

### Precedent alignment

This ADR extends, rather than introduces, house doctrine: ADR-0041/0042 already made FQN-exact + package-local resolution the resolver law for every ref-bearing attribute; this ADR carries that same law one tier further, into how a *resolved* node is *named* for emission. ADR-0023 ("nothing invented, nothing silently discarded") and the repo's "a gate that reports green while wrong is worse than no gate" precedent (#224/#225) both argue against any of the silent-wrong shapes in the "Context" section surviving. The repo-wide determinism discipline (stable, order-independent emission) is what makes decision §3's "pure function of the closure" requirement non-negotiable rather than a nice-to-have.

## Consequences

- **Non-colliding common case: byte-identical output, all ports.** No consumer sees any change unless their own metadata actually contains a same-short-name collision reachable from one payload artifact.
- **A newly-introduced collision is a visible, compile-time rename**, not a silent behavior change — the qualified name propagates to the declaration, the file/module (where applicable), and every reference in one coordinated regen.
- **Error code `ERR_PAYLOAD_NAME_COLLISION`** joins the payload/template build-time-error family (peer of `ERR_VAR_NOT_ON_PAYLOAD`). Stage 1 (TS + C#) declares it **locally** in each port's payload-codegen module rather than immediately in the shared cross-port error-code ledger (`packages/metadata/src/errors.ts` `ERROR_CODES` / `fixtures/conformance/ERROR-CODES.json`): that ledger is coverage-checked per port (TS asserts full bidirectional agreement; Python asserts its `ErrorCode` enum is a superset of the corpus), and registering the code before every port implements the corresponding fix would turn ports that haven't shipped it yet red for a codegen path they don't run. That promotion landed in 0.19.3 with the Java/Kotlin/Python payload-record follow-up: the code now lives in the shared cross-port error-code ledger — `fixtures/conformance/ERROR-CODES.json` plus TypeScript `errors.ts`, Python `errors.py`, and Java `ErrorCode.java` (the registries that gate against the corpus) — with C# and Kotlin retaining a port-local constant of the same value, so #228's shared TS/Python collision-naming modules source it from the ledger rather than redeclaring it.
- **Corpus contract strengthened, not weakened.** `fixtures/template-output-render-conformance/xpkg-collision/README.md` now states plainly: a port's conformance runner must construct its render-time payload from **generator-emitted** types — never hand-author or otherwise reconcile the payload record. The corpus's render-output pins (`"Alpha=AA Beta=BB"`) are untouched: the render engine and the build-time verify field-tree resolve against **metadata**, never against record names, so this ADR does not touch them.
- **Stage 1 (this decision):** the TS reference implementation (`codegen-ts/src/payload-codegen.ts`) and the C# port (`MetaObjects.Codegen/PayloadCodegen.cs`, fixing #219's wrong-node resolution as part of the same pass) ship together. **Stage 2/3 (tracked separately, not in this change):** Python, then Java + Kotlin (the heavier lift — per-output-package closure plumbing plus #220's new collision-conformance suite), followed by a coordinated bug-fix release across all four package registries.
- **Follow-up, explicitly out of scope here:** #219's own note that the C# port's `CSharpNaming.StripPkg` + bare-short-name-match convention recurs in roughly seven other C# generators (routes, entity, M:N navigation, output-parser, DbContext, reverse-finders, package-binding-resolver) — the same disease, a different blast radius (entity/route naming rather than payload naming), deserving its own audit and ruling. **Update (#228):** the *output-parser* member of that list — the extract/output-parser tier's own collision-scoped payload naming, plus the package-blind build-time `@payloadRef`/`@responseRef` resolvers it shares with the render-helper, output-prompt, and (JVM) `meta:verify` template-drift generators — is now fixed, cross-port (all five ports, not scoped to C#). The other six C#-specific generators in that list (routes, entity, M:N navigation, DbContext, reverse-finders, package-binding-resolver) remain open, tracked separately.
