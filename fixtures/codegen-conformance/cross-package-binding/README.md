# `cross-package-binding/` — codegen binds the target a reference names

One metadata input every port's codegen test loads, and `expected-bindings.json`, a
port-neutral DECISION TABLE: for every relationship and `identity.reference` in the input,
the object it binds to (by resolution key) and, for a relationship, the physical tables and
join fields the generated code must use. Like `shared-provided-enum/`, it records a
RESOLUTION, never generated bytes, so each port keeps its own idiom.

The rule it gates is ADR-0059 Decision 7: a consumer without a referrer reads the bound
target or resolves the canonical value exactly, never by short name, and never re-applies
the package of the node that inherits an attribute.

Two traps, each built so a short-name lookup and an inheritor-package lookup both bind the
wrong object, because the wrong object loads first (`meta.a.json` and `meta.acme.json` sort
before `meta.b.json` and `meta.root.json`). Each decoy is an `object.value`: two ENTITIES that
pluralize to the same collection name are refused by codegen (`ERR_COLLECTION_NAME_COLLISION`),
and a value object gets no collection, so the whole model still generates.

| Relationship | Names | Wrong binding a defect produces |
|---|---|---|
| `a::Post.tags` (M:N via `a::PostTag`) | `b::Tag` (table `b_tags`) | the value object `a::Tag`, the first `Tag` loaded |
| `a::Post.featuredTag` (to-one) | `b::Tag` | `a::Tag` |
| `acme::Order.customer` (to-one, inherited from root `BaseOrder`) | root `Customer` (table `customers`) | the value object `acme::Customer`, by short name or by resolving the inherited bare `Customer` in `acme` |
| `acme::Order.labels` (M:N via root `OrderLabel`, inherited) | root `Label` (table `labels`) | the value object `acme::Label` |

The root-level `BaseOrder` writes `Customer` and `Label` bare. After `resolveReferences`
they stay bare, which means the root-level object (ADR-0059 Decision 6), and they keep
meaning that when `acme::Order` inherits them.
