# TypeScript docs — generator entries, not a separate command

> Part of the `metaobjects-codegen` skill's TypeScript reference. Read it when generating or wiring documentation.

## Contents
- Six docs factories, each one more entry in `generators`
- Give them a `docs` target
- An owned docs generator goes in `generators`, like any other owned copy
- There is no `mermaidErDiagram()` generator
- Before calling any generated code, read `<targets.docs.outDir>/api/AGENT-API.md`
- Ejecting routes hands over the adapter too
- Wire a generator only for output you consume, and narrow it with its `filter`

**Documentation is `meta gen` generators — there is no separate `meta docs` command and
no `docs` config block** (both removed in 1.1.0, ADR-0034 Amendment 9: one way to
generate, docs included). Each factory is an ordinary entry in `generators`, from
`@metaobjectsdev/codegen-ts/generators`:

| Factory | Registry name | Writes |
|---|---|---|
| `docsFile()` | `docs` | the neutral model surface — one page per entity and per template (`<Entity>.md`, `<Template>.md`), plus an overview with the whole-model ER diagram. Options: `apiSurfaces`, `templates`. |
| `apiDocsFile()` | `api-docs` | the api reference — `api/<Entity>.md`, `api/README.md`, `api/AGENT-API.md`: the concrete imports, signatures, payload field shapes and runnable examples for THIS project's generated code. Options: `subDir` (default `api`), `modelBaseUrl`. |
| `requirementsFile()` | `requirements` | the declared `requirement.*` ledger, each entry headed by its dotted path and `title`. Writes nothing for a model with no `requirement.*` node. |
| `agentDocsFile()` | `agent-docs` | `agent/schema.md`, `agent/ui.md` (only when the run also lists a client-tier generator, OR the config sets `includeUiTier: true` — the escape hatch for a docs-only config whose UI is generated by a separate config; skipping it with a UI surface in the model and `includeUiTier` unset prints an advisory naming `includeUiTier`; `includeUiTier: false` says there is no UI anywhere and skips it without one) and `agent/requirements.md` — the three `agent/` pages the always-on pointer reads before touching a tier. |
| `metamodelDocsFile()` | `metamodel-docs` | the built-in vocabulary reference, under `metamodel/` (was `meta docs --metamodel`). |
| `docsSiteFile()` | `docs-site` | an HTML site under `site/` (was `meta docs --site`). Option: `prompts`. `meta eject docs-site` copies its templates and assets to `codegen/docs-site/` (was `meta docs --scaffold-site`). |

```ts
import { defineConfig } from "@metaobjectsdev/cli";
import {
  agentDocsFile, apiDocsFile, docsFile, entityFile, requirementsFile, routesFile,
} from "@metaobjectsdev/codegen-ts/generators";

export default defineConfig({
  outDir: "src/generated",
  targets: { docs: { outDir: "./docs/generated" } },
  generators: [entityFile(), routesFile(), docsFile(), apiDocsFile(), requirementsFile(), agentDocsFile()],
});
```

```bash
npx meta gen                                                     # runs every listed generator, docs included
npx meta gen --generators docs,api-docs,requirements,agent-docs  # documentation only
```

**Give docs factories a `docs` target.** Each defaults to the target named `docs`
(`targets.docs.outDir`) unless you pass `target`; a run that lists one while `targets` has
no `docs` entry is refused, naming the generator — documentation is never written into the
code's output directory by default. In a repository with more than one port, give each port's documentation its own
directory (`./docs/generated` here, `docs/csharp` and `docs/python` for those ports): another port's generated pages count as foreign files, and in a shared
directory each port's `verify --codegen` reports the other ports' pages as drift.

`--generators <names>` narrows a run to entries `generators` already declares, by registry
name (`meta gen --list` prints them); it never adds one, and naming an entry the config
does not declare is refused. A config still carrying a 1.0 `docs: { ... }` block fails
`meta gen` and `meta verify --codegen` before writing anything, naming the block. Full
before/after and the flag-to-option table: <https://github.com/metaobjectsdev/metaobjects/blob/main/docs/features/migrations/docs-are-generators.md>,
section "TypeScript".

**An owned docs generator goes in `generators`, like any other owned copy.** `meta eject
docs` (or `api-docs`, `requirements`, `agent-docs`, `metamodel-docs`) copies the generator
and prints the import and the entry to add to `generators` — there is no separate
`docs: { generators: [...] }` block to put it in any more.

**There is no `mermaidErDiagram()` generator.** `docsFile()` draws the ER diagram on its
overview page and on each entity's page with nothing else wired. A config that still
imports it, or names `"mermaid-er"`, fails with a message that says so; delete the entry
and run `meta gen`.

**Before calling any generated code, read `<targets.docs.outDir>/api/AGENT-API.md`**
(`./docs/generated/api/AGENT-API.md` with the config above) — it has the exact imports,
signatures, payload field shapes, and runnable examples for this project's generated API,
so you don't have to guess them.

From `@metaobjectsdev/codegen-ts-react`: `formFile()` → `<Entity>.form.tsx`.
From `@metaobjectsdev/codegen-ts-tanstack`: `tanstackQuery()` → `<Entity>.hooks.ts`
(5 React Query hooks), `tanstackGrid()` → `<Entity>.columns.tsx`,
`tanstackGridHook()` → `<Entity>.grid.tsx`.

`entityFile({ allowlists: false })` drops the allowlist-type import
for edge/worker consumers that don't mount server routes.

**Ejecting routes hands over the adapter too.** `meta eject routes` (and `routes-hono`,
and `entity`, whose allowlist TYPES come from the same tier) also copies the HTTP-adapter
source the emitted code calls — the mount helpers, filter parser, error envelopes and
pagination — verbatim from `@metaobjectsdev/runtime-ts/src` into `codegen/runtime/`. The
ejected generators point their output there (`../../codegen/runtime/drizzle-fastify/index.js`),
so after ejecting, generated and copied code import **no** `@metaobjectsdev/runtime-ts`;
install what eject prints instead (`qs`, `@types/qs`, the framework, the core
`@metaobjectsdev/metadata`). A route defect in the adapter is yours to fix in that copy.
What stays a package import is core: `@metaobjectsdev/metadata`, `render`, the reply
parser. Options on each ejected generator: `runtimeImport` moves the copy (relative to the
output root, like `dbImport`, or a path alias); `runtimeImport: "@metaobjectsdev/runtime-ts"`
goes back to the package. `meta eject --list --format text` and `meta gen --list` mark each
copied file identical to or differing from the installed package (the structured form of
`meta eject --list` omits those rows); to take an upstream fix, read
`diff -u node_modules/@metaobjectsdev/runtime-ts/src/<file> codegen/runtime/<file>` and
apply it (or `meta eject <name> --force` for a file you never changed).

**Wire a generator only for output you consume, and narrow it with its `filter`.**
Every generator factory takes `{ filter?: (entity) => boolean }`, ANDed with the
generator's built-in gates — so it can only NARROW what emits, never widen it:
`tanstackQuery({ filter: (e) => e.name !== "InternalAudit" })` emits no hooks for
that entity. There is no `@emit*` metadata attribute to do this — `@emitTanstack`,
`@emitRoutes`, `@emitForm`, `@emitGrid` and `@emitAngular` were never registered
vocabulary, so they passed `meta gen` and failed `meta verify`. If a project carries
one, `meta upgrade --apply` removes it.

The one thing a `filter` can't express is opting a TPH subtype IN to its own
per-subtype grid (that WIDENS): `tanstackGrid({ tphSubtypeGrids: (e) => … })`,
default `() => false`. Pass the same predicate to `tanstackGridHook()` or you get
a `<Sub>.grid.ts` whose `<Sub>.columns.tsx` is never emitted.
