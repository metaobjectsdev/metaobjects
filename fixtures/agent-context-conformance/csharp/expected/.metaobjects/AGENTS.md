# Working with MetaObjects in this project

> Stack: csharp server, no client.
>
> Generated by MetaObjects (refresh: `meta init --refresh-docs`). Put project notes in your
> root `AGENTS.md` or `CLAUDE.md`, not here: this file is regenerated.

The metadata (`metaobjects/` unless `.metaobjects/config.json` says otherwise) is the source of
truth. Code, schema and migrations are generated from it and are disposable.

## Start here: the whole loop, in order

### C#: generate with `dotnet meta gen`

1. **Config.** `codegen/Generators.cs` (written by `dotnet meta init`) is the generator list.
   Nothing is generated until it is listed. The EF Core data layer and its routes:

   ```csharp
   new MetaObjects.Codegen.Generators.EntityGenerator(),
   new MetaObjects.Codegen.Generators.DbContextGenerator(),
   new MetaObjects.Codegen.Generators.FilterAllowlistGenerator(),
   new MetaObjects.Codegen.Generators.RoutesGenerator(),
   ```

   `RequirementTestsGenerator { OutDir = "<tests project>/Generated" }` writes one test per
   requirement; `ApiDocsGenerator` writes `api/csharp/AGENT-API.md`. `dotnet meta gen --list`
   is the catalog.
2. **Generate.** `dotnet meta gen`. `dotnet meta eject <name>` copies a generator into the repo
   to change what it emits.

### Schema (every stack: the Node `meta` CLI owns it, so Java, C# and Python projects need Node too)

Never hand-write DDL, and never `ALTER` a live database by hand.

- First migration (needs a reachable, empty database):
  `npx meta migrate --from-db --db <url> --dialect <dialect> --slug init` writes
  `.metaobjects/migrations/<timestamp>-init/up.sql` and `down.sql`.
- At boot or deploy: `npx meta migrate apply-pending --db <url>`.
- A later change: edit the metadata, regenerate, then
  `npx meta migrate --dialect <dialect> --slug <name>` (offline, from the committed snapshot).
  A renamed field needs `--rename-column <table>.<old_column>=<new_column>` (an object:
  `--rename-table <old>=<new>`) to keep its data. A destructive change is refused until you
  allow its kind by name: `--allow drop-check` for a changed enum, `--allow drop-column` only
  when the data should go.

### Requirements, when the metadata declares `requirement.*` nodes

A commit that changes behaviour updates them in the same commit: `@status: live` once a claim
is built (never before), a new node for new behaviour.

### Before you call it done

- `dotnet meta verify --codegen` (the generated code and the requirements).
- `npx meta verify --db <url>` (the live schema matches the metadata).

Commit the metadata, the generated code, `.metaobjects/migrations/` and
`.metaobjects/.gen-state/.hashes.json`.

## Calling the generated REST API

When the project serves the generated routes (any port):

- Filter as `?filter[<field>][<op>]=<value>`: `?filter[status][eq]=active`, never
  `?status=active` (TypeScript refuses that with 400; the other ports ignore it and return every
  row). Operators: `eq`, `ne`, `isNull` (`true`/`false`), `in` (comma list, at most 100), `like`
  (case-sensitive, `%` and `_`), `gt`, `gte`, `lt`, `lte`. Filters AND; only `@filterable`
  fields filter.
- `?sort=<field>:asc|desc`, `?limit=N&offset=N`; `withCount=1` returns `{"rows", "total"}`.
  Always send `limit`: without it TypeScript and C# return every row, the other ports 50.
- `PUT` is the same partial update as `PATCH`.
- Errors are `{"error": "<code>"}`: 400 for validation (only TypeScript adds `issues`) and for
  a bad filter or sort (`invalid_filter_field`, `_op`, `_value`, `invalid_sort`, each naming
  `field`), 404 `not_found`, 409 for a unique or foreign-key conflict.

## Rules

- What the metadata describes is generated, never hand-written (tables, types, validators,
  foreign keys, schema, migrations). Hand-write only what it cannot describe, on top.
- Never hand-edit generated output: change the metadata and regenerate. Output wrong for you, or
  broken? Fix the generator: eject it and it is yours, no permission needed, nothing to wait on.
- Never spell a table or column name as a string; use the generated table or names constants.
- Wire a generator only for output you will import.
- An LLM prompt in a project that declares `template.prompt` is a declared template
  (`metaobjects-prompts`); a grouped total or report view is an `object.report`
  (`metaobjects-authoring`). Open the skill before writing either by hand.
- Never invent metadata vocabulary. Search it: `npx meta types <term>`, and
  `npx meta types <type>.<subType> --detail` for one construct's valid attributes.
- Metadata nodes are fused-key maps, `{"field.string": {"name": "email"}}`. Attribute names are
  unique within a node, and package paths use `::`.

## Going deeper

The loop above needs no skill. For less common work load a `metaobjects-*` skill by name, or open
`.claude/skills/<skill>/SKILL.md` if your assistant does not load skills: `metaobjects-authoring`
(unusual shapes, reports, adopting existing code), `metaobjects-codegen` (owning or writing a
generator), `metaobjects-runtime-ui` (REST routes, the web client), `metaobjects-prompts` (LLM
prompts), `metaobjects-verify` (migration edge cases, drift, upgrades), `metaobjects-audit` (an
adoption review). Each names the one reference page to open.

`meta init --refresh-docs` regenerates this file and the skills, so keep project guidance in
the root `AGENTS.md` or `CLAUDE.md` (or copy a skill to a new name). A refresh never overwrites a
file you edited; it writes `<path>.new` beside it, which you merge into `<path>` and delete.
Never `--force` a refresh over local edits.
