# Working with MetaObjects in this project

> Stack: python server, no client.
>
> Generated by MetaObjects (refresh: `meta init --refresh-docs`). Put project notes in your
> **root `CLAUDE.md`**, not here — this file is regenerated.

The metadata (`metaobjects/` unless `.metaobjects/config.json` says otherwise) is the source of
truth. Code, schema and migrations are generated from it and are disposable.

## Start here: the whole loop, in order

### Python: generate with `metaobjects gen`

1. **Config.** `metaobjects.config.yaml` names each target's `outDir` and its generators. Nothing
   is generated until it is listed:

   ```yaml
   targets:
     app:
       outDir: generated
       generators: [entity, names]     # Pydantic models + physical-name constants
   ```

   `routes` and `filter-allowlist` add FastAPI routers over a repository `Protocol` you
   implement; `requirement-tests` writes one pytest file per package of requirements;
   `api-docs` writes `api/python/AGENT-API.md`. `metaobjects gen --list` is the catalog.
   Install what the output imports: `pip install "pydantic[email]>=2" fastapi`.
2. **Generate.** `metaobjects gen`. `metaobjects eject <name>` copies a generator into the repo
   to change what it emits.

### Schema (every stack: the Node `meta` CLI owns it)

Never hand-write DDL, and never `ALTER` a live database by hand.

- First migration (needs a reachable, empty database):
  `npx meta migrate --from-db --db <url> --dialect <dialect> --slug init` writes
  `.metaobjects/migrations/<timestamp>-init/up.sql` and `down.sql`.
- At boot or deploy: `npx meta migrate apply-pending --db <url>`.
- A later change: edit the metadata, regenerate, then
  `npx meta migrate --dialect <dialect> --slug <name>` (offline, from the committed snapshot).
  For a renamed field add `--rename-column <table>.<old_column>=<new_column>` (a renamed object:
  `--rename-table <old>=<new>`), which keeps the data. A destructive change is refused until you
  allow its kind by name, and the refusal names it: `--allow drop-check` for a changed enum,
  `--allow drop-column` only when the data should go.

### Requirements, when the metadata declares `requirement.*` nodes

They list what the software must do. A commit that changes behaviour updates them in the same
commit: `@status: live` once a claim is built (never before), a new node for new behaviour.
`meta verify` checks that links resolve, not that a status is true.

### Before you call it done

- `metaobjects verify` (the generated code and the requirements; `--codegen` is its default).
- `npx meta verify --db <url>` (the live schema matches the metadata).

Commit the metadata, the generated code, `.metaobjects/migrations/` and
`.metaobjects/.gen-state/.hashes.json`.

## Rules

- What the metadata describes is generated, never hand-written (tables, types, validators,
  foreign keys, schema, migrations). Hand-write only what it cannot describe, on top.
- Never hand-edit generated output: change the metadata and regenerate. Output wrong for you, or
  broken? Fix the generator: eject it and it is yours, no permission needed, nothing to wait on.
- Never spell a table or column name as a string; use the generated table or names constants.
- Wire a generator only for output you will import.
- Once the project declares a `template.prompt`, every LLM prompt is one: the text in a
  template, the data in a payload, a structured reply read through its generated extractor
  (`metaobjects-prompts`).
- A grouped total, dashboard number or read-only report view (per client, per month) is an
  `object.report` over `dimension.*` / `measure.*` (`metaobjects-authoring`,
  `references/declaring-reports.md`). A hand-written `@sql` view body is the last resort.
- Never invent metadata vocabulary. Search it: `npx meta types <term>`, and
  `npx meta types <type>.<subType> --detail` for one construct's valid attributes.
- Metadata nodes are fused-key maps, `{"field.string": {"name": "email"}}`. Attribute names are
  unique within a node, and package paths use `::`.

## Going deeper

The loop above needs no skill. The `metaobjects-*` skills hold the detail for less common work:
unusual shapes or adopting existing code (`metaobjects-authoring`), owning or writing a
generator and the full principles (`metaobjects-codegen`), REST routes and the web client
(`metaobjects-runtime-ui`), LLM prompts (`metaobjects-prompts`), migration edge cases, drift and
upgrades (`metaobjects-verify`), an adoption review (`metaobjects-audit`). Load one by name when
its task comes up; it names the one reference page to open.

This file and the skills are regenerated by `meta init --refresh-docs`; put project guidance in
the root `CLAUDE.md`, or copy a skill to a new name to override it. A refresh never overwrites a
file you edited (only `--force` does, so never `--force` one with local edits): it writes
`<path>.new` beside it. Merge that into `<path>`, keeping your edits, and delete the `.new`.
