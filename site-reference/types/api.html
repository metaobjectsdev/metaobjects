Metamodel — api types

Each section below is one api.<subType>. The Attributes table lists the subtype's own + concern-contributed attributes (provider-tagged); universal documentation attributes are omitted here (see providers.md). Allowed children lists the structural child rules with their cardinality (min..max, * = unbounded).

api.base

Registry anchor for the declared API surface (ADR-0030, ADR-0054): not authorable. The api subtype axis is the interaction model, never the protocol; protocol lives in binding.* on each operation.

Attributes

No subtype-specific attributes.

Allowed children

No structural children.

api.operational

A named, packaged request/response surface whose children are operations (ADR-0030). It is a wire contract: two of them (v1, v2) may declare the same operation side by side. The code behind it is one service per metadata package, whose surface is the package's operations (ADR-0064).

Rules: Children are operation.command and operation.query. Lives at the document root. Declares no fields, sources or identities: shapes are referenced, never defined, by the surface.

When to use: The application does something beyond derived CRUD: a named command (approve, cancel, import) or a named query (my open requests). Declare it here so its input, output, permission and business errors are part of the model. A plain lifecycle needs no api.operational at all: each transition nobody claims derives its own command.

Attributes

No subtype-specific attributes.

Allowed children

  • operation.* — 0..*
