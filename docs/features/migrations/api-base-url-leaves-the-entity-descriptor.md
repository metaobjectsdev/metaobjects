# The API base URL leaves the entity descriptor (0.25.0)

**Applies to:** TypeScript client tiers — `@metaobjectsdev/tanstack` and
`@metaobjectsdev/angular`, and the code generated by
`@metaobjectsdev/codegen-ts-tanstack` / `@metaobjectsdev/codegen-ts-angular`.

**Not affected:** generated server routes, `apiPrefix` in `metaobjects.config.ts`,
the REST wire contract, and every non-TypeScript port.

## What changed

`$apiPrefix` is gone from the generated `<Entity>` descriptor (and from
`<Entity>.meta.ts`). Generated hooks and Angular services now emit **entity-relative**
paths, and the base URL is supplied once, at runtime, by the fetcher provider.

```diff
 export const Customer = {
   $entity: "Customer",
   $table: "customers",
   $path: "/customers",
-  $apiPrefix: "/api",
 } as const;
```

## What you change

One line, at the provider.

**React / TanStack**

```diff
-<EntityFetcherProvider value={fetcher}>
+<EntityFetcherProvider fetcher={fetcher} baseUrl="/api">
```

**Angular**

```diff
-provideEntityFetcher(fetcher)
+provideEntityFetcher({ fetcher, baseUrl: "/api" })
```

Pass whatever your `apiPrefix` says. If `apiPrefix` is `""` — what `meta init`
scaffolds — you can omit `baseUrl` entirely; it defaults to `""`.

The `value` prop is **gone**, not deprecated, so an unmigrated app fails `tsc` rather
than 404ing in a browser. That is deliberate: a missing base is otherwise invisible
until a request runs.

If your own code read `<Entity>.$apiPrefix`, it no longer compiles. Take the base from
the same config your provider does.

## Why

`apiPrefix` is an application setting — it has never been metadata (zero occurrences in
`expected-registry.json`, none in any `spec/metamodel/*.json`). For the **server** it is
correctly baked in at build time: the code that registers `/api/customers` *is* the
server, and that half is unchanged.

For the **browser** it is a deployment fact, and codegen was freezing it at `meta gen`
time. That meant a client bundle could not be built once and served against a different
origin — a separate API host, a dev proxy, a preview environment, an SSR pass that needs
an absolute URL. Now it can:

```tsx
<EntityFetcherProvider fetcher={fetcher} baseUrl={import.meta.env.VITE_API_BASE}>
```

It also removes one application setting that was being stamped into every entity's
constants file.

This matches how comparable tools have always drawn the line — the base URL is client
configuration supplied once (openapi-fetch's `createClient({ baseUrl })`, NSwag's
`API_BASE_URL` token, Apollo's `uri`, tRPC's `httpBatchLink({ url })`, axios's
`baseURL`), while generated per-operation code carries only the relative path.

## Notes

- `baseUrl` accepts a path (`/api`) or a full origin
  (`https://api.example.com/v1`); a trailing slash is handled.
- The base is a **sibling** of the fetcher, not something to hide inside it. Your
  fetcher stays a pure transport and receives an already-prefixed URL — so it can be
  reused, and the base can change without touching it.
- Nested providers still override, base and all.
- On the first `meta gen` after upgrading, a project whose `apiPrefix` is non-empty gets
  a one-time note naming the `baseUrl` to set. It does not repeat.
