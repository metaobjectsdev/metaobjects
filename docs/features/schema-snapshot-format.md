# The schema snapshot format

The expected schema is the store-neutral contract between a model and a database: the tables,
columns, keys, indexes, checks and views the metadata implies. This page describes how it is
written down as JSON. The same document is two things:

- what `meta schema --as json` prints, the expected schema with nothing applied anywhere;
- what `meta migrate` commits as `.metaobjects/migrations/.schema.<dialect>.json`, the schema
  the committed migration chain has reached.

A native migration tool (EF Core, Flyway, Liquibase, Alembic, sqlx) or a port's own tooling can
read it to know what the model expects without running the Node engine. `meta migrate` is one
way to apply that schema, not the only one.

The TypeScript definitions are the source: `SchemaSnapshot` and its descriptors in
`server/typescript/packages/migrate-ts/src/types.ts`, and the writer and reader in
`server/typescript/packages/migrate-ts/src/snapshot/serialize.ts` (`serializeSnapshot`,
`parseSnapshot`).

## Producing it

```bash
meta schema --dialect postgres --as json            # print it
meta schema --dialect sqlite --as json --out schema.json
meta schema --dialect postgres                      # the same schema as CREATE statements
```

`meta schema` builds the expected schema exactly as `meta migrate` does: the project's schema
conventions (`migrate.conventions`), `migrate.scope` and the dependency exclusion, and the views
that projections and reports lower to. It reads no database and no snapshot, and writes nothing
unless `--out` is given. The DDL form is what `meta migrate` would create for an empty database.

The dialect is `--dialect`, else `migrate.dialect` in `.metaobjects/config.json`, else `dialect`
in `metaobjects.config.ts`. The document is dialect-specific in its details (a view's body, a
check's expression, whether a table has a `schema`), so produce it for the dialect you deploy.
MySQL has no expected schema: MetaObjects does not own a MySQL schema.

## The file

```json
{
  "formatVersion": 4,
  "snapshot": {
    "tables": [ /* table descriptors */ ],
    "views": [ /* view descriptors */ ],
    "meta": { "sqliteVersion": "3.44.2" }
  }
}
```

The writer makes it byte-stable, so a diff of two documents is a diff of the schemas:

- object keys are sorted at every level, and the indentation is two spaces, with a trailing newline;
- `tables`, `views`, and each table's `columns`, `indexes`, `foreignKeys` and `checks` are sorted by `name`;
- an optional field that does not apply is left out, never written as `null`.

`meta` is optional. It records facts about the database the snapshot was taken against
(today only `sqliteVersion`), so the expected schema `meta schema` prints never has it.

## Table

| Key | Type | Meaning |
|---|---|---|
| `name` | string | The table's physical name, after `naming` (ADR-0058) |
| `schema` | string, optional | The database schema. Absent on SQLite and D1; on Postgres absent means `public` |
| `columns` | column[] | See below |
| `primaryKey` | string[] | The primary key's column names, in key order; `[]` for none |
| `primaryKeyName` | string, optional | The key constraint's name, when the conventions name it something other than `<table>_pkey` |
| `indexes` | index[] | See below |
| `foreignKeys` | foreign key[] | See below |
| `checks` | check[] | `{ name, expression }`: a named CHECK constraint and its boolean SQL |
| `description` | string, optional | From the entity's `@description`; a Postgres table comment |

## Column

| Key | Type | Meaning |
|---|---|---|
| `name` | string | The physical column name |
| `sqlType` | SQL type | The dialect-neutral type, below |
| `nullable` | boolean | Whether the column takes NULL |
| `default` | `{ kind, value }`, optional | `kind` is `literal` (a value) or `expr` (SQL such as `now()`) |
| `identity` | `"increment"` or `"uuid"`, optional | The key is generated by the database |
| `sequence` | `{ name?, start? }`, optional | An `increment` key's sequence, only as the model declares it (`@sequenceName`, `@sequenceStart`) |
| `description` | string, optional | From the field's `@description`; a Postgres column comment |

### SQL type

`sqlType` is a tagged object keyed by `kind`. The dialect renderers turn it into SQL, so the
same document describes the type on every dialect:

| `kind` | Extra keys | Notes |
|---|---|---|
| `text` | `maxLength?`, `variant?` (`varchar` or `char`) | `variant` is an `@dbColumnType` spelling |
| `integer` | `bits` (32 or 64) | |
| `real` | | Double precision (`field.double`) |
| `real4` | | Single precision (`field.float`) |
| `numeric` | `precision?`, `scale?` | |
| `boolean`, `date`, `time`, `json`, `blob`, `uuid`, `inet`, `interval` | | `inet` and `interval` are native on Postgres |
| `timestamp` | `withTimezone` | |
| `array` | `element` (an SQL type) | A native array, such as `uuid[]` |

## Index

| Key | Type | Meaning |
|---|---|---|
| `name` | string | The index's database name |
| `columns` | string[] | Key columns in order; `[]` when `expr` is the key |
| `unique` | boolean | `identity.secondary` is unique, `index.lookup` is not (ADR-0040) |
| `orders` | (`asc` or `desc`)[], optional | Per-column direction; absent is all ascending |
| `where` | string, optional | A partial index's predicate |
| `expr` | string, optional | An expression index's key |
| `using` | string, optional | The access method (`gin`, `gist`, ...); absent is the default |
| `constraint` | `"unique"`, optional | The conventions want this key as a UNIQUE constraint rather than an index |
| `plainIndex` | `true`, optional | The conventions want this key as a plain unique index |

## Foreign key

| Key | Type | Meaning |
|---|---|---|
| `name` | string | The constraint name |
| `columns` | string[] | The referencing columns |
| `refTable` | string | The referenced table's physical name |
| `refColumns` | string[] | The referenced columns, positional to `columns` |
| `onDelete`, `onUpdate` | `cascade`, `set-null`, `restrict` or `no-action`, optional | From the relationship's `@onDelete` / `@onUpdate`; absent is the database default |

## View

| Key | Type | Meaning |
|---|---|---|
| `name` | string | The view's physical name (`@view`) |
| `schema` | string, optional | As for a table |
| `sql` | string, optional | The view body, the `SELECT` through its tail |
| `fingerprint` | string, optional | `metaobjects:v1:sha256:<hex>`, the body's hash, which `meta migrate` stamps in the view's comment |
| `dependsOn` | string[], optional | The tables the view reads |

A snapshot `meta migrate` took from a database can also record a view's `dependents`, the
relations that depend on it. The expected schema never has them.

## Versions

`formatVersion` is bumped when a descriptor gains a field. A reader refuses a document newer than
it knows and upgrades an older one:

- 2: tables gained `checks`.
- 3: views gained `fingerprint` and `dependents`.
- 4: a comment and a generated identity read back from a database are recorded, so absence means
  none, not unknown.
