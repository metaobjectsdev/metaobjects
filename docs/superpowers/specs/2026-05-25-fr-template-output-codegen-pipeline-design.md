# FR: `template.output` codegen pipeline (structured LLM output)

**Status:** Design proposal — needs brainstorm before implementation
**Date:** 2026-05-25
**Scope:** Cross-language — `template.*` is a cross-port vocabulary (Tier 1 invariant per
the cross-language porting principle). This FR proposes a codegen story for the
`template.output` subtype that mirrors what `template.prompt` already has.
**Origin:** An adopter using `template.prompt` for prompt construction asked the obvious
follow-up: when an LLM is supposed to return *structured output* (JSON-schema-shaped),
where's the typed-codegen story for that direction?

## Current state

The `template.*` metatype has two concrete subtypes:

| Subtype | Codegen status |
|---|---|
| `template.prompt` | **Shipped.** `generateRenderHandle()` + `generatePayloadInterfaces()` emit a typed `renderXxx(payload): { text, model }` handle that interpolates the prompt template with type-checked payload data. |
| `template.output` | **Declared, but no first-class codegen path.** The current `generateRenderHandle()` handles both subtypes identically — text rendering, no structured-output schema generation. Adopters wanting JSON-schema-style typed output from LLMs have no codegen support. |

`template.output` is part of the FR-004 vocabulary (cross-language), but the *output*
direction — "produce a JSON Schema / TypeScript type / Pydantic model from the
`template.output`'s declared `@payloadRef`" — was deferred.

## Goal

Bring `template.output` codegen to parity with `template.prompt`:

1. **TypeScript:** generate a `parseXxx(text: string): T | { error }` function alongside
   `renderXxx(payload)`. The parser uses the linked `@payloadRef`'s value-object schema
   (already generated by `generatePayloadInterfaces`) plus a JSON-shape validator
   (likely Zod, matching the rest of the TS surface).
2. **Cross-language:** each port that ships payload-VO codegen also ships an output-parser.
   C# is most likely already structurally close (its render engine handles both subtypes
   per CLAUDE.md); the question is whether parsing is symmetric.

## Why this is cross-language

`template.output` is in the cross-port vocabulary (Tier 1 invariant). Every port that
implements FR-004 needs to handle both subtypes; the codegen direction (how the typed
parser is generated) is a per-port concern but the *schema* the parser validates against
(the `@payloadRef`-linked value-object structure) is cross-language.

## Brainstorm topics (open)

### 1. Schema source: declared payload vs. JSON Schema artifact

Today `template.prompt` references its payload via `@payloadRef` — pointing at an
`object.value` declaration in the metadata. The same mechanism is available to
`template.output`. The output-parser codegen could:

**(a) Use the same `@payloadRef` and the same value-object structure.** Symmetric with
prompt; consumers can use the same VO type for both input and output (rare but valid).

**(b) Introduce a separate `@outputRef` for outputs.** Asymmetric. Maybe needed if
output schemas diverge from input shapes (LLM produces fields the prompt doesn't take).

Recommendation hypothesis: **(a)** — symmetry is valuable; nothing prevents declaring a
separate output VO and pointing `@payloadRef` at it. Brainstorm should confirm with
real consumer use cases.

### 2. Parser implementation: Zod, JSON Schema, or hand-written?

For TypeScript:
- **Zod** — matches the rest of the TS surface (`@metaobjectsdev/codegen-ts` already
  emits Zod schemas for entity validation). Consumer's bundle is already paying for it.
- **Generated JSON Schema + a runtime validator like Ajv** — broader interop, but adds a
  dep.
- **Hand-written narrowing logic** — no runtime dep, but more codegen complexity.

Recommendation hypothesis: **Zod**, matching the rest of the TS pipeline.

For C#: System.Text.Json with source generators is the obvious match. For Python:
Pydantic v2. For Java: TBD when Java codegen ships.

### 3. Error shape: throw vs. result-type vs. provider-specific

LLM outputs frequently fail to parse (hallucinated fields, wrong types, truncation).
The generated `parseXxx(text)` needs an error-handling shape:

**(a) Throw on invalid.** Caller wraps in try/catch.

**(b) Return a discriminated union.** `{ ok: true, value: T } | { ok: false, error: string }`.
Matches the rest of the TS surface where errors are values.

**(c) Provider-specific shape.** OpenAI's structured-output mode handles this internally;
Anthropic's tool-use does too. Maybe the parser is dual-mode: strict validation if the
caller asks, lenient if not.

Recommendation hypothesis: **(b)** — explicit error values, matches existing patterns.

### 4. Interaction with prompt/output paired templates

A common pattern: a prompt and an output are paired — same workflow, prompt asks for
data, output validates the response. Should codegen surface a paired-handle that
combines them?

```ts
// Hypothetical
const { renderInput, parseOutput } = workflows.councilGeneration;
const { text } = renderInput({ ... });
const result = parseOutput(llmResponse);
```

This is pure convenience; brainstorm whether it's worth the API surface.

### 5. Cross-port rollout order

Suggested:
1. Schema choices (decisions 1–4 above) settled cross-language in an ADR.
2. TypeScript impl first.
3. C# follows (already most of the way; per CLAUDE.md it ships `verify` against
   `template.*`, just need to extend codegen if not already done).
4. Python / Java when those ports ship their payload-VO codegen.

## Tests required when this lands

- TS conformance fixture: `template-output-and-prompt` already exercises round-trip;
  add `expected/parsers.ts` showing the output-parser codegen.
- TS unit tests on the generator + a snapshot.
- TS integration test exercising the round-trip against a mock LLM response — both
  success and validation-failure paths.

## Out of scope (until brainstorm)

- Streaming output parsing. The generated `parseXxx` is non-streaming; streaming is a
  separate concern.
- LLM-provider-specific response handling (OpenAI tool-use, Anthropic structured output).
  The parser takes a `string` and produces a typed result; provider integration is on
  the consumer's side.
- A higher-level "workflow" abstraction that chains prompt → call → output. That's a
  separate FR if there's appetite.

## Open questions

1. Is there an existing internal use case driving `template.output` shape today, or is
   this purely a "fill the symmetry gap"? The brainstorm should ground in real demand,
   not theoretical.
2. Should the C# implementation be cross-checked first? Per CLAUDE.md, C# already
   "renders the shared `fixtures/render-conformance` corpus byte-identical to TS" — if
   C# already has structured-output codegen and TS is the gap, that changes the rollout
   sequence.
3. How does this interact with `meta verify` (FR-004 build-time drift gate)? Today
   `meta verify` checks template variable ↔ payload-field drift; should it also check
   output-parser schema ↔ payload-VO drift?
