# FR6 — `template.output` parser-on-receipt codegen (cross-port design)

**Status:** Design — plan-of-record
**Date:** 2026-05-25 (post-brainstorm)
**Scope:** Cross-port parent design. Per-port implementation FRs follow:
[FR6-ts](./2026-05-25-fr6-ts-template-output-parser.md),
[FR6-csharp](./2026-05-25-fr6-csharp-template-output-parser.md) (sketch),
[FR6-python](./2026-05-25-fr6-python-template-output-parser.md) (sketch),
[FR6-java](./2026-05-25-fr6-java-template-output-parser.md) (sketch).
**Depends on:** [ADR-0010](../../../spec/decisions/ADR-0010-template-output-parser-codegen.md) (the cross-port principle); existing FR-004 payload-VO codegen (TS shipped 0.6.0; C# shipped per CLAUDE.md).

## Goal

For every declared `template.output`, codegen emits a typed parser that validates LLM
response text against the value-object referenced by `@payloadRef` and returns
typed data (or a structured failure, per port idiom). `meta verify` extends to cover
output drift symmetric with prompt drift.

```ts
// Consumer side, after FR6-ts
import { parseNpcResponse, safeParseNpcResponse } from "./generated/NpcResponse.output";
import { renderNpcPrompt } from "./generated/NpcPrompt";

const { text: promptText } = renderNpcPrompt({ scenario: "..." });
const llmResponse = await myLLMProvider.call(promptText);

// Strict (throws on bad shape):
const npc = parseNpcResponse(llmResponse);

// Safe (Result-style):
const r = safeParseNpcResponse(llmResponse);
if (!r.success) { /* handle r.error */ } else { /* use r.data */ }
```

## Why

The 80% case for `template.output` is **parse-on-receipt** — every LLM consumer has
text arriving from somewhere (provider with or without structured-output mode,
streaming or batch, retries, fallbacks) and needs to extract typed data. Today
`generateRenderHandle()` treats `template.output` as just-another-text-renderer and
ignores the structured-output direction; adopters write the parser by hand.

ADR-0010 captures the design principles. This FR is the cross-port implementation
spec.

## Design

### What codegen emits per port

Each port emits a parser file derived from each `template.output` declaration.
The file shape is per-port idiomatic (see ADR-0010 table), but every port's
generated parser:

1. **Imports the payload-VO** referenced by `@payloadRef` (already generated by
   `generatePayloadInterfaces()` in TS, equivalent in other ports).
2. **Builds a schema/validator** matching that VO's structure — using each port's
   native validation library (Zod for TS, Pydantic for Python, Jackson for Java,
   System.Text.Json for C#).
3. **Exposes a parser API** in the port's idiomatic shape:
   - **TS:** `parseXxx(text): T` (throws) + `safeParseXxx(text): Result`.
   - **C#:** `ParseXxx(string)` (throws) + `TryParseXxx(string, out, out)` (bool).
   - **Python:** `parse_xxx(text: str) -> Xxx` (raises).
   - **Java:** `parseXxx(String text)` (throws checked or unchecked).
4. **Documents the failure mode** in the generated code's docstring / JSDoc /
   XML doc (the soft cross-port contract from ADR-0010).

### What codegen does NOT emit

- Provider-side schema artifacts (OpenAI `response_format`, Anthropic tool
  definitions, etc.). Adopters that want provider-side enforcement derive it from
  the same `@payloadRef` themselves, or wait for a follow-on FR.
- A combined "workflow" handle (render-prompt → LLM-call → parse-output). The
  LLM-call layer varies per adopter (provider, model, streaming, retries) and is
  not the codegen's business.

### `@payloadRef` semantics

Symmetric with `template.prompt`:

- `template.prompt`'s `@payloadRef` points at the **input** value-object — the
  data the prompt is interpolated against.
- `template.output`'s `@payloadRef` points at the **output** value-object — the
  shape the LLM is expected to produce.

Adopters needing different in/out shapes declare two `object.value` VOs and
point each template at one. No new attribute (`@outputRef`) is introduced.

### `meta verify` extension

The existing `meta verify` command (FR-004 Plan #3 T6, shipped 0.6.0) extends:

- Today: walks `template.prompt` nodes, derives variables, checks against
  `@payloadRef`'s payload-VO field names.
- After FR6: also walks `template.output` nodes, derives parser-schema field
  names, checks against `@payloadRef`'s payload-VO field names.

Diagnostic output adds a `kind: "prompt" | "output"` field on each finding so
adopters and CI dashboards distinguish drift types.

Per-port `meta verify` equivalents (C# already has `verify`; Python/Java when
their CLIs ship) extend the same way.

## Cross-port testing strategy

- **Conformance fixtures.** The shared corpus already has
  `fixtures/conformance/template-prompt-simple/` exercising `template.prompt`. A
  new fixture `fixtures/conformance/template-output-simple/` adds the parallel
  for `template.output` (input metadata declaring a `template.output` with a
  `@payloadRef`; `expected/parsers.<ext>` showing each port's emitted parser).
- **Round-trip + codegen test.** Each port's conformance harness verifies its
  emitted parser matches the expected output for the fixture.
- **`meta verify` drift test.** A test fixture with intentionally drifted
  payload-VO ↔ template (e.g. payload renames a field; template still uses old
  name) verifies that `meta verify` raises a finding with `kind: "output"` for
  the output-side check.

## Out of scope (until follow-on FRs surface)

- Provider-side schema artifacts (OpenAI / Anthropic / Gemini).
- Workflow handle codegen (render → call → parse combined).
- Streaming-output parsing (parser takes a full string; streaming is consumer-side).
- Per-attribute parse-error attribution within the LLM response (today's parsers
  return one error; richer per-field diagnostics are a future enhancement).

## Open questions

None at the cross-port design level — every decision settled in the brainstorm.

Per-port questions (which validation library to use; exact exception type names;
whether to emit a barrel file) are owned by each per-port FR.
