# 1.1 plan — a solid core, and generators anyone can build

_Status: proposed, 2026-09-26. Follows the 1.0.9 cycle, in which five cold external reviews
and the adopter estate were run against successive release candidates._

## What the 1.0.9 cycle showed

About sixty findings, sorted by layer:

| Layer | Share | Trend |
|---|---|---|
| Reference helpers (`runtime-ts` HTTP adapters, Zod/Drizzle generators, and their equivalents in the other ports) | about half | never converged: each new app shape found a new edge |
| Core: `meta migrate` | 8 | serious, but converging; renames and rollback hold end to end by the last round |
| Core: prompt render and reply extract | 3 | real contract bugs, each fixed in all five ports with the corpus |
| Docs, CLI wording, the fit assessment | about 15 | cheap |
| Regressions introduced by fixes | 3 | two caught only by the adopter estate |

Every reviewer called the prompt-template drift gate and the migrate rename/rollback path the
strongest parts, and the helper tier the weakest. The helper tier re-implements what the web
framework ecosystems already harden (body parsing, error envelopes, query parsing, pagination,
date and time handling) once per port.

## The ruling this plan builds on

MetaObjects is a **core** — the typed model, loader and registry, `meta verify`, `meta migrate`,
prompt render and reply extract — and **adopters build their own generators** on it for whatever
they need. Shipped generators are examples and starting points. When one is ejected, the adopter
owns all of its code, including the runtime helpers its output uses (1.0.9). The skills and docs
teach writing a generator first and ejecting a reference second (1.0.9).

## 1.1 work

1. **Generators for the formats estates already use.** A JSON Schema generator and an OpenAPI 3.1
   generator as first-party references (1.0.9 ships them as tested examples to copy). Reviewers
   said repeatedly that a "contract layer" reads as OpenAPI and that the tool could not emit it.
   Emitting the standard formats lets adopters reuse every existing client and server generator
   (openapi-typescript, orval, openapi-generator's many languages) instead of waiting for a
   MetaObjects port. A protobuf emitter is a candidate after these two.
2. **Reference generators that target established libraries.** Generate TypeScript routes
   against the frameworks' own validation layers (a Fastify Zod type provider, `@hono/zod-openapi`)
   and schemas through `drizzle-zod` where it fits, so the generated code leans on hardened
   libraries rather than a MetaObjects runtime. Same principle in the other ports (ASP.NET
   minimal-API validation, Spring validation, FastAPI/Pydantic) wherever a reference still
   carries its own runtime code.
3. **A generator catalog that adoption can start from.** More small, focused references (a
   typed client, form schemas, fixtures and seed data, docs pages, event payload types), each an
   example to eject, each with a test that runs its output. The measure is time-to-first-own-
   generator for a new adopter, not the number of generators shipped.
4. **Evaluate Atlas as the migrate diff backend.** MetaObjects would keep deriving the desired
   schema from the model; Atlas (or drizzle-kit for TypeScript-only projects) would diff, lint
   and plan. Decide on evidence: run both against the estate's migration history and the
   persistence corpus, and compare the rename, rollback and hazard behaviour that the 1.0.9
   reviews exercised. Keep the in-house engine unless the comparison is clearly better.
5. **Keep the prompt tier as the differentiator.** Render, extract and the template drift gate
   stay core and conformance-gated in every port. The nearest comparable tools (BAML,
   Instructor, TypeChat) type the model call; none fails the build when a template drifts from
   its payload. Invest there: template location in errors, a response-format placement that
   templates can reference, and extract recovery cases from real replies.

## How releases are gated from here

- The adopter estate gate (`rc-gate.sh` plus the five-port contract suite) stays the promotion
  bar. It caught regressions that no corpus and no cold review did.
- A cold external review is run once per release, against the release candidate, and its
  findings are triaged by layer. Core findings block the release. Helper findings are fixed in
  the reference, and do not block, because adopters own their copies.
- Open-ended review rounds are not a release gate: each new app finds the next helper edge, which
  measures surface area, not readiness.
