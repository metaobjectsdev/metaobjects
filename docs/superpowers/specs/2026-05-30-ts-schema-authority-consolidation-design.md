# TS as the Single Schema Authority — Consolidation Design

_Date: 2026-05-30_

## Problem / motivation

Schema migrations are moving to a **TS-only** approach ([[ts-only-schema-migrations-pivot]]). Today every language port (Java/OMDB, C#, Python, Kotlin) carries its own schema machinery — expected-schema builder, live-DB introspection, diff, migration emit/apply, and aggregate-view DDL synthesis. That is duplicated, drift-prone, and (per the 2026-05-30 OMDB review) the least-mature code in each port.

We will make **TypeScript the single authority for database schema**: DDL generation + apply (migrations), view synthesis, and **schema-drift detection**. The other ports become **pure data-access runtimes** — they read/write rows against a schema that TS provisioned; they never build, migrate, introspect, diff, or synthesize schema. Two capabilities the existing per-port engines provided are **high-value and must be preserved** (not lost in the removal):

1. **Aggregate/projection view synthesis** (`origin.aggregate`/`origin.passthrough` → `CREATE VIEW … SELECT … GROUP BY …`). **Already production-ready in TS** (`codegen-ts` `extractViewSpec` + `emitViewDdl`, wired through `meta migrate`). Nothing to build — only to make it the single source.
2. **Live-DB schema-drift detection** (a CI gate: "does the live DB match the metadata-declared schema?"). TS has the machinery (`migrate-ts` `introspect` + `buildExpectedSchema` + `diff`) but **no gate command** and **no view-body drift detection**. This is net-new (small/medium) TS work.

## The model

- **TS owns schema.** `meta migrate` generates + (eventually) applies DDL including views; `meta verify --db` is the drift gate.
- **Ports are pure data-access.** Java/C#/Python/Kotlin remove all migration/expected-schema/introspect/diff/view-synthesis code. They keep CRUD/query/codec/transactions/runtime mapping only.
- **Conformance schema is one TS-owned artifact.** The persistence-conformance corpus carries a **TS-produced canonical schema DDL** (`schema.<dialect>.sql`, generated from `canonical/meta.fitness.json`, regenerated by a TS step and drift-checked). Every port's query-scenario runner **executes that committed SQL** to set up its test DB, then runs query scenarios. No port synthesizes schema (this is what Kotlin already does with its checked-in `ProgramStatView.VIEW_DDL`; we generalize it and make TS the producer).
- **Migration conformance is TS-only.** The `fixtures/persistence-conformance/migrations/*` scenarios are exercised only by TS. Query + api-contract scenarios still run on every port (against the committed schema DDL).

## Components

### 1. TS schema-drift gate — fold into `meta verify --db`
- `meta verify` stays **DB-free by default** (current behavior: prompt/template/payload drift via `@metaobjectsdev/render`). Unchanged for projects that don't pass a DB.
- Add `meta verify --db <conn> --dialect <postgres|sqlite>` (+ `--d1`/`--remote` parity with `migrate` where relevant): run `introspect(liveDB)` + `buildExpectedSchema(metadata)` + `diff()`, and **exit non-zero if any change is present** (drift). Emit a human-readable list of drift (tables/columns/indexes/FKs/**views**).
- **View-body drift** (the gap): introspection currently reads view *names* only. Extend it to read view *definitions* (`pg_views.definition` / `sqlite_master.sql`) and compare bodies — reuse the `migrate` command's existing textual view-body comparison (`readExistingViewSql` + `classifyViewDiff`) so a changed aggregate/projection body is flagged, not silently ignored.
- Flag semantics satisfy all three cases: always-check (run `meta verify --db` in CI), sometimes-ignore (omit `--db`, or a `--skip-schema` escape), never-need (never pass `--db`).

### 2. Corpus schema-DDL artifact
- A TS tool (extend the conformance tooling or a small script) generates the canonical schema DDL — base tables + the `v_program`/`v_program_stat` views — from `fixtures/persistence-conformance/canonical/meta.fitness.json`, and writes `fixtures/persistence-conformance/canonical/schema.<dialect>.sql`.
- Commit it; add a regenerate + **drift-check** step (CI fails if the committed DDL diverges from what TS would generate — keeps the artifact honest). This is itself a nice dog-fooding of TS-owns-schema.
- **Dialect scope (decision below):** at minimum Postgres (all JVM/C#/Python conformance runs on Testcontainers Postgres). TS view synthesis supports postgres + sqlite (+ d1); Derby is NOT supported by TS.

### 3. Port query-runner rewire (all 5)
- Each port's persistence-conformance query runner stops building schema from metadata and instead **executes `canonical/schema.<dialect>.sql`** against its test DB, then runs query scenarios via its runtime data-access layer.
- TS runner: already synthesizes; switch it to consume the committed DDL too (single source), OR keep TS as the generator-of-record and have it apply its own output — TBD in plan.

### 4. Remove per-port schema engines
- **Java/OMDB:** Phase-1 removal (the diff-and-converge engine + `meta:migrate`/`meta:verify` mojos + `render(Change)`) is **already done on branch `omdb-migration-removal`** (Option A kept the runtime auto-create validator for the harness). Once the harness consumes the committed DDL (component 3), **also remove** the runtime auto-create path (`MetaClassDBValidatorService` + legacy `createTable`/`createIndex`/`createForeignKey` DDL) so Java is truly pure data-access — *unless* we choose to keep it as a dev convenience (decision below).
- **C#:** remove the incremental-migration engine / introspect / diff / `PostgresSchema.CreateView` (per [[csharp-migration-pipeline-status]]); keep EF Core runtime data-access + the entity codegen (codegen is separate from migration). Confirm the `meta` C# CLI's `migrate`/`--from-db` is removed.
- **Python:** remove `metaobjects.migrate` (build_expected_schema/diff/emit) + the runtime that synthesizes views; keep the ObjectManager/SQLAlchemy data-access.
- **Kotlin:** remove `ExposedMigrationEngine` + migration codegen; keep Exposed data-access. (Kotlin already ships a checked-in view DDL — aligns.)

### 5. Conformance + docs
- Migration scenarios → TS-only; update the corpus README protocol (schema provisioned from committed DDL, not per-port `meta migrate --from-db`).
- Update `spec/`, per-port docs, CLAUDE.md (pillar wording: drift detection schema-coverage is now `meta verify --db`; ports are data-access), and the conformance memories.

## CLI architecture (cross-language)

Commands split into two categories, and that split resolves the "is `meta` now Node-specific?" question:

- **Per-language commands** (`gen`, `init`, codegen/runtime `verify`) are inherently language-specific (`codegen-spring` is Java, `codegen-ts` is TS, …) and run in **each language's own build toolchain** — `mvn …:gen` (Java/Kotlin Maven plugin), a `dotnet`/MSBuild task (C#), a console-script/build hook (Python), the Node `meta` CLI (TS). A single CLI cannot do another language's codegen, so there is no unified codegen binary by design.
- **Schema commands** (`migrate`, `verify --db` drift) operate on the **shared canonical metadata + a DB connection** — language-agnostic. They live in **one canonical Node `meta` CLI**, used by **any** project regardless of backend language. Schema is thus a **standalone tool, like Flyway / Liquibase / Atlas / sqitch** — not re-implemented per language.

Decisions (locked 2026-05-30):
- **One canonical `meta` = the Node CLI**, owning schema (`migrate`, `verify --db`) for all backends, plus TS codegen + `init`.
- **Ship the Node `meta` CLI as a standalone single-file binary** (Node SEA / `bun build --compile` / Atlas-style per-OS binaries) so non-TS adopters need **no Node toolchain** — just the binary, for dev/CI schema ops. The app runtime never depends on Node.
- **Per-language codegen is invoked via that language's build tool**, NOT a competing global `meta` binary. **Reconcile the C# `meta` dotnet-tool** (which would collide on PATH with the Node `meta`) to `dotnet meta` / an MSBuild task so the bare `meta` is unambiguously the schema+TS CLI.
- **No proxying** (a per-language CLI shelling to a bundled Node) and **no per-language binary names** (`meta-ts`/`meta-java`) — both rejected (proxying re-couples the boundary + bundles Node everywhere; renaming is churn that doesn't answer who-owns-schema).

| Concern | Tool | Who runs it |
|---|---|---|
| TS codegen, `init` | Node `meta` CLI | TS projects |
| Java/Kotlin codegen | `mvn …:gen` (Maven plugin) | JVM projects |
| C# codegen | `dotnet meta` / MSBuild task | .NET projects |
| Python codegen | console-script / build hook | Python projects |
| **Schema migrate + drift (`verify --db`)** | **Node `meta` CLI (standalone binary)** | **any project, any backend** |

## Cross-language contract impact
- **Persistence-conformance protocol changes:** "build schema via the port's migration engine" → "execute the committed TS-produced `schema.<dialect>.sql`." Update `spec/conformance-tests.md` / the corpus README.
- **Metamodel vocabulary unchanged** — `source.rdb`/`origin.*`/`@kind` etc. are authoring concepts; only *who turns them into DDL* changes (TS, once).
- **No wire-format impact.**

## Sequencing (phases — each independently shippable)
- **Phase 1 — Java engine removal** (DONE, parked on `omdb-migration-removal`): finalize + merge as the first step.
- **Phase 2 — TS schema commands:** `meta verify --db` drift gate (+ view-body drift detection) AND `meta migrate --apply` for postgres/sqlite (transactional, declarative/idempotent, reusing `--dry-run`/`--allow`); + tests. (The standalone-binary packaging can land here or in its own phase.)
- **Phase 3 — corpus schema-DDL artifact:** TS generator + committed `schema.<dialect>.sql` + regenerate/drift-check; rewire the **Java + Kotlin** runners to consume it (the JVM side first, since Java's harness currently leans on the kept validator).
- **Phase 4 — rewire TS/C#/Python runners** to the committed DDL; **remove the C#/Python/Kotlin migration engines**; remove Java's runtime auto-create (validator + legacy DDL) if the "fully pure" decision holds.
- **Phase 5 — migration conformance → TS-only; docs/spec/README/memories.**

Each phase ends with the standard gate (suite green → code-reviewer + code-simplifier → merge forward).

## Open decisions (confirm during planning)
1. **Conformance dialect standardization:** make ALL ports' *query* scenarios run on **Testcontainers Postgres** (so one TS-produced `schema.postgres.sql` serves everyone, and Java drops Derby for conformance) — vs. carry per-dialect DDL where TS supports it (postgres + sqlite) and keep Derby some other way (TS can't emit Derby). **Recommend: standardize query conformance on Postgres.**
2. **Java runtime auto-create:** in "fully pure data-access," remove `MetaClassDBValidatorService` + legacy `createTable` DDL once the harness uses committed DDL (recommended) — vs. keep it as an optional dev-only convenience. Same question for C#/Python "create-if-missing" conveniences.
3. **TS apply:** RESOLVED 2026-05-30 — **build real `meta migrate --apply` for postgres + sqlite.** Rationale: a one-command apply is materially better for agent/CI workflows than emit-then-run, and it's a modest lift because the model is **declarative/state-based** (introspect live DB → diff vs metadata → apply the diff in a transaction), so it is **idempotent by construction and needs NO migration-history/ledger table**. Reuse the existing `--dry-run` (preview) and `--allow` (destructive-change gate) safety rails; add a transactional executor. Pairs with the standalone binary for `meta migrate --apply --db <conn>`. Does NOT replace the conformance committed `schema.sql` (that stays so ports need no Node at test time); `--apply` is for real dev/prod provisioning + agent-driven changes.
4. **C#/Python `meta` CLI migrate surfaces** — RESOLVED by the CLI architecture above: schema (`migrate`/`verify --db`) is owned by the Node `meta` CLI, so C#/Python CLIs **drop their migrate/`--from-db` surfaces entirely** (keep codegen). The C# `meta` dotnet-tool is reconciled to `dotnet meta`/MSBuild to free the bare `meta` name.

**CLI model — RESOLVED 2026-05-30** (see "CLI architecture"): one canonical Node `meta` CLI owns schema for all backends, shipped as a standalone binary; per-language codegen stays in build tools.

## Non-goals
- Changing the metamodel vocabulary or wire format.
- Building MySQL/Oracle/MSSQL schema support in TS (TS targets postgres/sqlite/d1; commercial-DB *runtime* CRUD stays per-port via their drivers).
- Re-adding any migration logic to the non-TS ports.
