## 0. The decisions on one page

| # | Question | Ruling |
|---|---|---|
| D1 | What is the shared artifact, and how does it travel? | **One flattened canonical-JSON file plus a manifest, generated by the publisher's codegen and shipped inside the publisher's own ecosystem package** (Python package data, npm package files, a JAR's resources). This is the legacy resources-only metadata JAR, generalized: versioned with the package that implements it, pulled by the consumer's own package manager. |
| D2 | When does a consumer resolve it? | **At sync time.** `meta deps sync` locates the installed package through a transport (`path`, `npm`, `python`; `maven`/`nuget` in Phase 2), copies the artifact into a committed snapshot (`.metaobjects/deps/<name>/`) and records a content hash in a committed lock. Every port then loads plain files. The legacy "read straight off the classpath at build time" is recorded as the Phase-2 JVM option; the committed snapshot is the cross-port contract (§2.1 states the trade-off). |
| D3 | What does a publisher declare? | A **generator**, not a hand-written export list: `sharedModelFile({ name, include, exclude, files })` selects top-level nodes by the existing scope-pattern grammar (config-level, no metamodel attribute), proves the selection is closed, and emits `<name>.metaobjects.json` + `metaobjects.pkg.json`. `meta verify --codegen` gates both. | D4 | Consumer declaration | `dependencies: [{ name, <transport>, mode }]` in `.metaobjects/config.json`, read at every rung of the source ladder; `mode` is `reference` (default: a model owned elsewhere) or `own` (the legacy pattern: I instantiate these objects — generate, migrate, claim). |
| D5 | May a consumer extend or overlay a foreign object? | **Yes, both — expected, documented, taught in the skills.** Dependency files load first; consumer files after; the loader's existing overlay merge and deferred `extends` do the rest. **A consumer contribution to a foreign node must say `overlay: true`** so that its disappearance upstream is loud (`ERR_OVERLAY_NO_TARGET`), never a silent new object. |
| D6 | What fails when upstream changes? | Two gates. **At load, every port:** the loader's own errors when a target the consumer built on is gone or incompatible (enumerated in §2.5). **At sync/check, Node:** a **usage-aware** breaking-change classification — the canonical diff of every foreign node the consumer extends, overlays or references, scoped to how each is used (whole node for `extends`/`@objectRef`, key-and-table for an FK), with a fail-closed rule for "significantly changed" (§2.6). `sync` refuses a BREAKING upstream without `--accept-breaking`; `verify --deps` reports it. |
| D7 | What is "foreign", and what does tooling do with it? | A node is foreign iff its FQN is in a dependency's exported `nodes` (from the lock) — one predicate, `Collection.foreignOwner(fqn)`. `reference` mode: referenceable, extendable, overlay-able for non-structural additions; never emitted, migrated or claimed; imports resolve through per-port `packageBindings` (the FR-025 slice, Phase 1b). `own` mode: treated as the consumer's own objects. A structural overlay (field / identity / index / relationship / source / TPH subtype) on a `reference`-mode node is refused — the consumer does not own that schema. |
| D8 | Phasing | Phase 1a = TS + Python + corpus, the cutover path. 1b = bindings + docs badge. Phase 2 = Java/Kotlin + C#, plus the JVM classpath read and `maven`/`nuget`. Phase 3 = deferred (§9). |

## 1. Problem

### 1.1 The general case

A shared model — abstracts, enums, value objects, sometimes entities — is maintained in one
repository and referenced from others, in other languages. The loader mechanics shipped long
ago (source composition, overlay merge, deferred cross-package `extends`, FQN-exact
references). Missing is the **convention**: how a model is packaged, which parts of it are
public, how a consumer declares the dependency, how every port finds the same bytes, how a
consumer builds on it, and how the consumer learns that upstream moved under it.

### 1.2 The driving case (real, generalized)

- **A library project** owns a Python engine and a TypeScript platform. Its model is one YAML
  file under the platform (39 concrete entities, plus value objects, projections, abstract
  bases and an internal presentation overlay); the engine generates Pydantic models from slices of it.
  It writes a jsonb document into a table it does **not** own. It is installed by consumers
  as an editable checkout; it is on no registry.
- **A consuming app** is a Python application. Its Node `meta` is schema tooling only
  (`generators: []`, `meta migrate` owns its Postgres schema); its Python `metaobjects gen`
  emits physical-name constants only. It owns the table the library writes into and declares
  that column as an open bag because nothing it can see declares the shape.

The library's requirement declares the document as an `object.value`; the app's plans to
**vendor a copy** and hand-write a drift test. FR-023 replaces that. And per ruling 4 the
library's shared artifact is not one document: it is every shape a downstream app is likely
to reference, extend or overlay (PRIVATE appendix, part E).

### 1.3 The legacy pattern this must resemble

Studied in the archived Java line (`metaobjects-core`, read-only, "implementation moved to
the monorepo") and its two sibling consumers. The pattern, with the code that implemented it:

1. **Shared metadata as a versioned resources-only JAR.** `examples/shared-resources/pom.xml`
   is a `jar` module whose only content is `src/main/resources/metadata/examples-metadata.json`
   ("No dependencies — this is just resources"). Everything was `-SNAPSHOT`, deployed through
   `distributionManagement`; a sibling enterprise consumer pulled snapshots from GitHub
   Packages with `<snapshots><enabled>true`.
2. **Downstream pull = an ordinary `<dependency>`, read straight off the classpath — no
   unpack.** `examples/basic-example/pom.xml` declares the shared jar; the loader tries the
   classloader chain *before* the filesystem (`FileMetaDataSources.getInputStreamForFilename`,
   `getResourceViaClassLoaderChain`: the sources' own loader → the loader handed in by the
   Maven MOJO → system); URIs `model:resource:` / `classpath:` (`URIHelper`); Spring
   auto-scans `classpath*:metadata/*.json` so every jar on the classpath contributes. The
   Maven plugin builds that classpath from `project.getRuntimeClasspathElements()` +
   `getCompileClasspathElements()` (`AbstractMetaDataMojo.createProjectClassLoader`).
   `maven-dependency-plugin unpack` appears nowhere.
3. **Internal-only metadata stayed out by file placement alone.** No filter was ever
   implemented (`LoaderParam.filters` is declared and read by nothing). The shared jar carried
   the base file; the consuming module kept `*-overlay.json` beside it (`fishstore-base-
   metadata.json` vs `fishstore-db-overlay.json`; the archetype's `application-metadata.json`
   vs `database-overlay.json`).
4. **Local overlays loaded after the shared file, in list order** (`<sources>` order in the
   pom; `FileMetaDataLoader.loadSourceFiles`). `BaseMetaDataParser.createOrOverlayMetaData`
   matched by `type + package::name`, parsed the overlay's attrs and children onto the
   existing node, wrapped an inherited match via `overload()`. **`overlay=true` threw when the
   target was missing** ("Overlay operation requested … but no existing metadata found");
   without the flag it **silently created** a new node, and JSON's laxer `override: true`
   **silently skipped** on a miss.

Two lessons carry forward unchanged and one is corrected: (a) the artifact rides the
ecosystem's normal dependency; (b) overlays are the local-additions mechanism and the
shared file must load first; (c) the silent-create / silent-skip doors are the bug — the
current loader already throws `ERR_OVERLAY_NO_TARGET`, and §2.5 makes the explicit flag
mandatory for contributions to foreign nodes so a consumer can never fall through that door.

### 1.4 The 2026-06-11 sketch — kept, changed, rejected

| Sketch | v2 |
|---|---|
| Code-free artifact = `metaobjects/` tree + `metaobjects.pkg.json` | **Changed:** one generated flattened file + a generated manifest, inside the publisher's package (§2.2) |
| Published to npm / Maven / PyPI / NuGet as a separate code-free package; resolved per ecosystem at load time | **Changed:** rides inside the publisher's existing package (no fourth-registry publish of the same bytes — the stored prior-art finding); resolved at sync time (§2.1) |
| `metadataDependencies: [{ package, version }]` | **Changed:** `dependencies: [{ name, <transport>, mode }]`; the ecosystem pins the version, the lock pins the bytes |
| Dependency-then-local order; local overlay wins | **Kept** (ruling 2) — with the explicit-`overlay` requirement and the structural rule for `reference` mode |
| Same-package collision between two dependencies → error | **Changed** to per-node: two dependencies exporting the same FQN → `ERR_DEPENDENCY_NODE_COLLISION` |
| Manifest names required providers | **Deferred** — exports must load with core providers (§2.3 check 5) |
| `verify` reports per-dependency provenance | **Kept** (source ids + the `verify --deps` report) |
| Lockfile: open | **Yes**, plus the committed snapshot |
| YAML vs canonical JSON in packages | **Canonical JSON** — the artifact is generated, so the desugar variance question disappears |
| Generalize `libraries` | **Not in Phase 1**; `libraries` is exactly a dependency with `mode: own` and a shipped-in-toolchain transport — the alignment is Phase 3 (§9) |

## 2. Decisions and rationale

### 2.1 D1/D2 — The artifact travels inside the publisher's package; sync copies it; the snapshot is committed

**The artifact.** A publisher's shared model is one file, `<name>.metaobjects.json`, with a
sibling `metaobjects.pkg.json`. Both are **generated output** (§2.3) written to a directory
the publisher's package ships: for a Python package, package data under the package
directory; for an npm package, a directory listed in `files`; for a JVM artifact,
`src/main/resources/…` (Phase 2). The version that matters is the publisher's package
version, because the consumer installs that package to get the code that implements the
model — the metadata is versioned with what it describes, which is the legacy jar's
property and the reason a separate code-free package on four registries (the sketch's
plan, and the stored research's "notable negative": no surveyed project does that) is
not needed. A metadata-only library publishes the same two files in whichever ecosystem it
already uses, or is consumed by `path`.

**Sync = pull + extract.** `meta deps sync` resolves each dependency's installed package
through its transport, reads the manifest, validates (§4.1), copies the artifact into
`.metaobjects/deps/<name>/` and writes the lock. The consumer's own package manager did the
pull (`pip install`, `npm install`, `mvn`); sync does the extract — the step the legacy
loader did implicitly by reading the classpath.

**Committed snapshot versus build-time read — the reconciliation the ruling asked for.**

| | Committed snapshot (v2) | Build-time read from the installed package (the legacy classpath analogue) |
|---|---|---|
| Who implements transports | one tool (`meta deps`), once | every port, at every load: Python natively, Node by spawning an interpreter on each `meta migrate`, the JVM from the classpath, C# from NuGet content |
| Hermetic / offline | yes — CI runs `meta migrate`, `verify --db`, `metaobjects gen` without the upstream installed | no — the package must be installed wherever any command runs |
| What the reviewer sees when upstream changes | the **diff of the shared model** in the consumer's PR (one file) | a hash change in the lock |
| Drift detection | `verify --deps` compares lock ↔ installed package | the lock hash check at load (fails on every command until re-accepted) |
| Cost | a copied file in git that changes when upstream changes — the event you want visible | none in git; five transport implementations to keep in parity |

**Recommendation: committed snapshot.** The reviewable diff is the deciding property: the
ruling wants an upstream change to be a loud event a human acts on, and a diff of the model
in the consumer's history is that event; a hash is not. The JVM port may add the legacy
classpath read in Phase 2 as an opt-out (`"commit": false` — the Maven plugin populates the
same `.metaobjects/deps/<name>/` layout under `target/` from the jar at build time; the
lock still governs); no other port needs it. Deferred until a JVM consumer exists (§9).

**Transports** — a transport answers one question at sync time: *which directory holds
`metaobjects.pkg.json`?*

| Kind | Spec | Resolution |
|---|---|---|
| `path` | `{ "name": "x", "path": "../lib/pkg/metaobjects" }` | the directory, relative to the declaring config's directory; the dev-loop override |
| `npm` | `{ "name": "x", "npm": "@acme/model", "dir": "metaobjects" }` | `createRequire(<configDir>/package.json).resolve("@acme/model/package.json")`'s directory, then `dir` (default: the package root) |
| `python` | `{ "name": "x", "python": "acme_model", "dir": "metaobjects" }` | `importlib.util.find_spec(<module>).submodule_search_locations[0]`, then `dir`; interpreter ladder `$METAOBJECTS_PYTHON` → `$VIRTUAL_ENV/bin/python` → `<configDir>/.venv/bin/python` → `python3`; the interpreter used is printed. `find_spec` imports the parent packages, so the interpreter is the consumer's own environment |
| `maven` / `nuget` | Phase 2 | the local repository artifact (`~/.m2`, the NuGet cache), unzipped at sync |

Exactly one transport key per spec (strict schema). `git` is deferred: install through the
ecosystem's git support, then use the ecosystem kind (§9).

### 2.2 D3 — The publisher's artifact is generated by `sharedModelFile()`

**Why a generator and not a hand-written manifest.** Three properties fall out of making the
artifact codegen output: it is **drift-gated** (`meta verify --codegen` regenerates and
diffs it, so a model edit that changes the public surface cannot ship unnoticed); it is
**closure-checked at gen time** (a selection that references something it does not include
fails the build with the pair named); and it is **hand-edit-refused** like every other
generated file. A hand-written `files:` list has none of these, and the legacy `.bundle`
line-list had none either. This is the maintainer's "flattened file" suggestion, evaluated
in full in §2.9 against file-level export.

**Selection is config-level, by the scope grammar.** `include` / `exclude` take the same
`acme::platform::**` patterns as `scope` — strings, portable to every port's config,
already gated by `scope-conformance`. No metamodel attribute marks a node public; ADR-0023
would demand a can't-be-computed justification, and a marker cannot be computed *because it
is a policy*, which is exactly why it belongs in config (the v0.3 strategy already ruled
"`@private` would be a hint, not enforcement"; the stored prior art records that every
surveyed tool keeps "what is a collection" in config). `files` restricts which of the
publisher's own source files contribute — the legacy file-placement mechanism, kept: an
internal presentation overlay (`view.*`, `layout.*` on the same nodes) is excluded by not
listing its file, with no per-child provenance surgery.

```ts
// metaobjects.config.ts (publisher)
import { sharedModelFile } from "./codegen/generators/shared-model"; // ejected, owned (ADR-0034)

export default defineConfig({
  generators: [
    entityFile(), /* … */,
    sharedModelFile({
      name: "acme-platform",                 // the dependency key consumers will use
      version: undefined,                    // default: the nearest package.json / pyproject version
      files: ["metaobjects/meta.platform.yaml"],   // own source files that may contribute (default: all own sources)
      include: ["acme::platform::**"],
      exclude: ["acme::platform::FeatureFlag", "acme::platform::*View"],
      target: "shared",                      // an output target the package ships
    }),
  ],
  targets: { shared: { outDir: "../../engine/acme_platform/metaobjects" } },
});
```

```yaml
# metaobjects.config.yaml (a Python publisher) — same options under a target
targets:
  shared:
    outDir: acme_platform/metaobjects
    generators: [shared-model]
    options:
      shared-model:
        name: acme-platform
        files: [../platform/metaobjects/meta.platform.yaml]
        include: ["acme::platform::**"]
        exclude: ["acme::platform::FeatureFlag"]
```

**What it emits.**

```
<outDir>/
├── acme-platform.metaobjects.json    # ONE canonical-JSON document: a `metadata.root` with no root package;
│                                     # every top-level node carries its own `package`; raw (own-layer) form —
│                                     # `extends` PRESERVED, inherited members NOT flattened (§2.9 says why)
└── metaobjects.pkg.json              # the manifest (§3.2), incl. `nodes` and the artifact's sha256
```

**The algorithm** (§4.3 in full): standalone load of `files` with the run's registry →
select top-level nodes by `include`/`exclude` (always excluding `requirement.*` and
`template.*` — a publisher's ledger and prompts are not a consumer's shapes) → **closure
check**: every `extends` target and every `REF_BEARING_ATTR_NAMES` value of a selected node
(and of its descendants) resolves to a selected node, else fail naming `(referrer → target)`
pairs with "include it or exclude the referrer" (the same fail-loud stance `scope` takes;
auto-widening would silently publish an internal shape) → **re-load the emitted document
standalone with core providers, strict** — a consumer loads it with *its* providers, and
Phase 1 exports must not need the publisher's (§9) → emit both files.

**Versioning.** `version` defaults to the host package's version (TS: nearest `package.json`;
Python: `pyproject.toml` `[project].version`; Java Phase 2: `${project.version}`), so the
manifest's version is the version the consumer installed. `metamodelVersion` is the
toolchain's `METAMODEL_VERSION`. The publisher never edits either by hand.

### 2.3 D4 — Consumer declaration, lock, snapshot, and the source ladder

§3.1 gives the schema. Two points of substance:

**`dependencies` are read at every rung of the source ladder.** `metadata-sources.md`'s
ladder decides *where the project's own metadata lives*, and a port's native surface (the
Python `metadata:` key, the Maven `<sourceDir>`) owns that concern outright. `dependencies`
answers a different question — *what does my metadata build on that lives elsewhere* — and is
read from the neutral file whichever rung supplied the own sources. A dependency declared in
two files would be two answers.

**The lock pins bytes; the ecosystem pins the version.** `version` is recorded for humans and
the report; `integrity` (sha256 of the artifact bytes) is what `verify --deps` compares. The
ecosystem's own lock (`package-lock.json`, `uv.lock`, the pom) is what installs a version;
this lock records what that version's metadata *was* when the consumer last accepted it.

**Sync-time checks** (§4.1): manifest schema; `manifest.name == spec.name`; `metamodelVersion`
major equals the toolchain's (`ERR_DEPENDENCY_METAMODEL_INCOMPATIBLE`); the artifact's hash
equals the manifest's; the artifact loads standalone with core providers, strict, and its
top-level resolution keys equal `manifest.nodes` (`ERR_DEPENDENCY_MANIFEST_INVALID`); no two
dependencies export the same FQN (`ERR_DEPENDENCY_NODE_COLLISION`); the usage-aware
classification (§2.6) against the current snapshot.

**Load-time checks, every port, offline** (§4.2): config names == lock names; each lock
entry's artifact exists and hashes as recorded (`ERR_DEPENDENCY_SNAPSHOT_STALE`, message
names the fix: `meta deps sync`); no FQN collision across entries.

### 2.4 D5 — Overlays and `extends` of foreign nodes are allowed and expected

**What the consumer may do.** Load order is dependency artifacts first, consumer sources
after, in one `loader.load(...)` (the overlay-only partition still runs, so order is
immaterial). Then, exactly as within one project:

- **`extends` a foreign abstract** (the `BaseEntity` pattern across repos): the consumer's
  entity inherits the base's fields, a foreign abstract `field.enum` is reused by
  `extends`, a consumer projection borrows a foreign entity's identity. Deferred resolution
  finds the target in the merged tree; nothing new.
- **Overlay a foreign node** (`overlay: true`, same `package` + `name`): add presentation
  (`view.*`, `layout.dataGrid`), validators, documentation attrs, `@filterable`/`@sortable`
  — the local, unshared additions the maintainer describes; in `own` mode, anything at all,
  including persistence (`source.rdb`, `@column`, new fields) — the legacy
  `database-overlay.json`.
- **Declare new nodes in the dependency's package.** **REFUSED** —
  `ERR_DEPENDENCY_PACKAGE_NOT_OWNED` (§11.1 item 2, ruled 2026-09-11). This bullet
  previously read *"Allowed; the legacy consumers did."* That claim was checked against the
  legacy estate and is **false**: the one legacy consumer that declares into a shared
  package (declared across both a framework module and the app consuming it)
  adds **no** class the framework does not already declare — it amends, via the
  data/ui/baseui overlay split, and an amendment is an overlay, not a new node. See §11.5.
- **Reference** foreign nodes by FQN from any ref-bearing attribute. Bare references stay
  package-local (ADR-0042), so a consumer node *in the dependency's package* may use a bare
  name for a foreign sibling — the same rule as today, no exception.

**One requirement: a contribution to a foreign node must be explicit.** The parser merges a
same-`(type, package::name)` redeclaration whether or not it says `overlay: true`; only the
flagged form fails when the target is absent. Without the flag, an upstream removal turns the
consumer's amendment into a silent new local object — the legacy silent-create door. So a
local top-level node whose FQN is in a dependency's `nodes` must carry `overlay: true`, else
`ERR_DEPENDENCY_OVERLAY_IMPLICIT` ("add `overlay: true` — an amendment of a dependency's node
must fail loudly when that node disappears"). Detected post-load by the boundary validator
(§4.4) using the loader's existing raw-source overlay sniff (`_partitionOverlayLast`'s
walker, exposed as `declaredOverlayKeys(source)`); the merged tree does not record the flag
(the serializer deliberately drops it).

**The structural rule for `reference` mode.** A downstream app that does not own a table may
not change its shape (the library's own downstream-DB ADR says the same: "apps extend by
composition, not mutation; a downstream app never adds columns to a platform table"). So an
overlay of a `reference`-mode foreign node whose *local* contribution is a `field.*`,
`identity.*`, `index.*`, `relationship.*` or `source.*` child, a TPH subtype of a foreign
discriminator base, or a physical attribute (`@table`, `@schema`, `@column`, `@kind`) is
refused: `ERR_DEPENDENCY_SCHEMA_NOT_OWNED`, with the fix named ("declare your own object in
your own package and `extends` it, or take `mode: own` if you instantiate this model").
Local contributions are identified by the child's parse-time `source.files` (not
`dep:`-prefixed) — the one place source-id provenance is load-bearing rather than
diagnostic. Attr conflicts with the base stay `ERR_MERGE_CONFLICT` (existing).

### 2.5 D6(a) — What fails at load when upstream changed

The loader already fails the consumer's build when a target it built on is gone or
incompatible. After `meta deps sync` replaces the snapshot, these fire in every port, on
every command, with no new machinery:

| Upstream change | Consumer construct that breaks | Error (existing) |
|---|---|---|
| node removed or renamed (incl. package rename) | `overlay: true` on it | `ERR_OVERLAY_NO_TARGET` |
| | `extends` it | `ERR_UNRESOLVED_SUPER` |
| | `@objectRef` / `@references` / `@through` / origin heads / template refs to it | `ERR_UNRESOLVED_OBJECT_REF` / `ERR_INVALID_REFERENCE` / `ERR_INVALID_RELATIONSHIP` / `ERR_INVALID_ORIGIN` / `ERR_INVALID_TEMPLATE` / `ERR_PARAMETER_REF_UNRESOLVED` |
| member removed or renamed | dotted `extends: Foo.member` (ADR-0029) | `ERR_UNRESOLVED_SUPER` |
| | identity/index `@fields`, `layout.dataGrid @columns`, `@via` paths, `@filter` on inherited members | the existing validation-pass errors |
| member's type or subtype changed | dotted `extends` | `ERR_EXTENDS_TARGET_MISMATCH` |
| attr the consumer's overlay also sets now set differently upstream | the overlay | `ERR_MERGE_CONFLICT` |
| an object the consumer's overlay adds structure to went `object.value` → no source | overlay in `own` mode | the existing subtype-rule errors |

**What load cannot see** — a member's `subType`, `isArray`, `@required`, `@values`,
`@objectRef`, `@default` or physical name changed while every name stayed; a base's
`extends` retargeted; a `@maxLength` narrowed. The consumer's generated code and stored
data would drift silently. That is the second gate.

### 2.6 D6(b) — "Significantly changed", mechanically, at sync and check

**Footprint.** `F` = the foreign top-level nodes the consumer *uses*, each with the
**scope** of that use — because what a consumer depends on differs by how it depends. An app
holding a cross-schema FK to a 29-field telemetry entity depends on that entity's key and
table, not on its 27 other columns; an app storing a value object in its own jsonb column
depends on every member.

| How a local node uses a foreign node | Scope diffed |
|---|---|
| `extends` (any depth; a dotted target's owner) | **whole** node, closed over its own `extends` chain (inherited members are what the consumer sees) |
| `field.object` / `field.map` `@objectRef`; `@payloadRef` / `@responseRef` / `@parameterRef` | **whole** node + chain (the shape is stored or rendered) |
| `identity.reference @references`; relationship `@objectRef` / `@through`; origin heads `@from` / `@of` / `@via` | **key**: the target's `identity.*` children, its `source.*` children (an FK targets a table), and the specific members a dotted ref names (the `@of` field, the `@via` relationship) |
| `overlay: true` (a local contribution to the node) | **existence** + the node's `type.subType`; the attrs the overlay also sets (a value change there is `ERR_MERGE_CONFLICT` at load anyway); the parents of every locally-added child |
| `@implementedBy` | **existence** |

Computed from the loaded consumer model by one walker
(`dependencyFootprint(root, collection) → Map<fqn, { owner, scope }>`, widest scope wins
when a node is used two ways), never recorded in the lock (it would churn on every local
edit).

**Diff.** For each `f ∈ F`: `old` = `f`'s raw canonical subtree in the snapshot artifact,
`new` = in the fetched artifact, both restricted to the scope. A node-keyed structural diff
(children matched by `(type, name)`, attrs by name) yields leaf changes, each classified:

| Change | Class |
|---|---|
| `f` absent in `new`; a descendant node absent | **BREAKING** (the loader will also fail if the consumer targets it by name) |
| a node's `type.subType` key differs | **BREAKING** |
| `extends`, `abstract`, `isArray` differ | **BREAKING** |
| an attribute removed | **BREAKING** |
| an attribute's value changed | **BREAKING**, unless the change is in the **widening table** |
| an attribute added | **BREAKING**, unless in the **additive table** |
| a child node added | COMPATIBLE (reported) |
| a documentation attr (`description`, `title`, `notes`, `seeAlso`, `aliases`, `replacedBy`) changed | ignored |
| `deprecated` added | COMPATIBLE, reported as a deprecation notice |

Widening table (COMPATIBLE only in the stated direction): `@maxLength` up, `@minLength`
down, `@precision` up, `@max` up, `@min` down, `@required` true→false, `@values` superset,
`@intValueMap` superset with every existing entry unchanged. Additive table (an attr
appearing where none was): the documentation attrs, `@filterable`, `@sortable`. **Anything
not named in a table is breaking** — fail-closed, because the cost of a false BREAKING is
one `--accept-breaking`, and the cost of a false COMPATIBLE is silent data or codegen drift.

**Where it fires.**

- `meta deps sync`: classification runs before the snapshot is replaced. Any BREAKING →
  refuse (`ERR_DEPENDENCY_BREAKING_CHANGE`, exit 1) with the per-node report; `--accept-
  breaking [<name>]` proceeds, after which the load-time gate (§2.5) still holds until the
  consumer's model is fixed. COMPATIBLE-only → proceed, print the changes.
- `meta deps check` = `meta verify --deps`: same classification, nothing written; any
  upstream drift → `ERR_DEPENDENCY_UPSTREAM_DRIFT`, exit 1, BREAKING lines marked.
- The classifier is a pure function `(oldTree, newTree, footprint) → Change[]` in
  `@metaobjectsdev/metadata` with a Python twin, so the corpus asserts it in both ports
  and a Phase-2 `metaobjects verify --deps` can share it.

**How this interacts with the loader.** The classification never touches the loader; it
runs on two canonical documents. The loader's overlay merge and deferred `extends` are
unchanged; their errors are the first gate (§2.5). The one loader-adjacent addition is
the explicit-`overlay` requirement (§2.4), enforced post-load.

**Prior art, in one line each** (§2.10 for sources): `buf breaking` classifies a diff of the
*publisher's* two versions by category; Confluent's compatibility modes do the same for
Avro/JSON Schema; GraphQL operation checks and Salesforce's subscriber-field protection are
*usage-aware* — they refuse a publisher change that a consumer's known usage depends on. §2.6
is the usage-aware kind, run on the consumer's side because the publisher does not know its
consumers.

### 2.7 D7 — "Foreign", and what each surface does with it

**Definition.** `Collection.foreignOwner(fqn)` returns the dependency whose lock `nodes`
contains `fqn`, else `undefined`; `Collection.governs(fqn)` is `owner === undefined ||
owner.mode === "own"`. One helper each, threaded through the same seams `inScope` uses.
`isForeign` is `foreignOwner(fqn) !== undefined`.

| Surface | `reference` (default) | `own` |
|---|---|---|
| `gen`, `verify --codegen` | foreign nodes **not selected** (`scope: fqn => inScope(fqn) && governs(fqn)`); a consumer overlay's presentation children are not emitted either (the node is not emitted); an explicit `meta gen <Foreign>` / `entities: [Foreign]` is refused by name; the shared-enums artifact and Python's materialized-enum pass skip foreign abstract enums; a local artifact that *names* a foreign type imports it through `packageBindings` (§2.8) | treated as local: emitted, enums materialized |
| `migrate`, `verify --db` | foreign nodes leave the expected schema **and** their physical names are suppressed on the actual side — the two suppressions `migrate.scope` performs; reported "declared by dependency `<name>`"; a local FK to a foreign table is emitted as today (the table must exist) | treated as local: created, altered, dropped under the consumer's `migrate` — the consumer owns those tables, so `@schema` in the shared model is the consumer's business; documented with the library-ADR caution that a shared database has one owner per table |
| requirements ledger | foreign nodes excluded from the scan and the denominator; a local `@implementedBy` may name a foreign member | counted |
| `verify --templates` | foreign templates never arrive (the generator excludes them) | — |
| `docs` | foreign nodes render, badged "from dependency `<name>` `<version>`", with the consumer's overlay contributions marked as local; `--agent` pages include them | as local |
| `export`, `types` | unchanged — inspection over the loaded collection | — |
| loader validation passes | run over the merged model, unchanged | — |

`own` is the legacy consumer, and the shape `libraries: ["ai"]` already has (the consumer
owns `llm_call`). It is opt-in per dependency and the doc says when: *you instantiate this
model — you generate its code and own its tables* (a metadata-only library). For the driving
pair it is wrong: the library owns its tables. A per-node override (`own: ["…"]`) is
deferred (§9).

**Why not provenance.** A consumer overlay merges into the foreign node; the merged
envelope's `contributors` are sorted alphabetically, not by declaration, so provenance
cannot say which file was the base. That rules provenance out as the ownership test and is
unaffected by the 2026-09-11 ruling.

**Why `packages` and not `nodes` is the exclusion key (superseded this paragraph).** This
section previously argued for `nodes` on the grounds that "consumers may declare into the
dependency's package, so package ownership does not hold." The estate does not bear that
out (§11.5), and a per-object key costs a second mental model — "ownership is per node, not
per package" — for a case with no instance. The exclusion key is `packages`; `nodes`
remains in the manifest and lock for artifact integrity, collision detection, and the
`ERR_DEPENDENCY_PACKAGE_NOT_OWNED` refusal that makes the package rule fail loudly instead
of silently.

### 2.8 D7(b) — Codegen imports across the boundary (the FR-025 slice, Phase 1b)

Unchanged from v1 in substance: in `reference` mode a foreign named type is `@provided`
(ADR-0026) — referenced, never materialized — and the import comes from per-port
`packageBindings`, keyed by metadata package with per-FQN overrides winning (FR-025's
`overrides` / `typeOverrides` shape; a publisher that generates one package into several
modules needs the FQN form). Missing binding for a referenced `reference`-mode type → a
codegen error naming the package and the config key. `own` mode needs no bindings. The
existing `providedEnumModule` / `provided_enum_packages` are the same primitive and are not
renamed here. Not needed by the driving pair (schema-only Node, names-only Python).

### 2.9 The flattened-export generator versus file-level export — the evaluation

| Criterion | File-level export (v1) | Flattened generator (v2) |
|---|---|---|
| Contract stability | the contract is whatever files the publisher lists; an author editing a listed file for an internal reason changes the export | the contract is the selection; `verify --codegen` fails when the emitted surface changes, so a public-surface change is a reviewed diff of one file |
| Diffability | N source files, YAML, comments, ordering noise | one canonical JSON file, attribute keys alphabetized, deterministic — the diff *is* the model change |
| Internal-only filtering | by file only (the legacy limit): exporting one object from a 41-entity file means moving it | by file **and** by FQN pattern; an internal overlay is kept out by not listing its file; an internal entity by `exclude` |
| Selection marker | none | none — config-level scope patterns (ADR-0023 satisfied: a policy cannot be computed from the model, so it is not a metamodel attribute) |
| Closure | proven only by a separate gate | proven at gen time, in the generator, with the offending pair named |
| Downstream overlay / `extends` | attach by `(type, package::name)` | identical — the artifact is raw canonical form, the same declarations, so `overlay: true` and `extends` target the same keys |
| `extends` resolved or not | n/a | **not resolved.** A flattened-effective export would duplicate inherited members onto every child, break the consumer's own `extends` onto the exported abstract (it would no longer be a super-reference), and turn one upstream base change into N leaf diffs. Raw form is the interchange form (ADR-0006) and what the loader round-trips |
| Versioning | manifest by hand | manifest generated; version = the host package's |
| Drift check | hash of N files | hash of one file; the usage-aware diff runs on canonical trees, which the artifact already is |
| Multi-package export | fine | one document with node-level `package` (a root-level node may carry its own package — ADR-0029's addressing model); Task 2 verifies the serializer/parser round-trip and adds a fixture if none covers it |
| Cost | none | a second standalone load at gen time (a few files) and a third of the emitted string |

**Verdict: the generator.** It is the legacy jar's intent with the legacy's two gaps closed
(no filter; no closure check), and it makes the public surface a gated artifact instead of a
directory convention. File-level export survives only as the generator's `files` option.

**What recurs, and where v2 lands.**

1. *Mutable name → immutable pin + content hash, with an explicit fetch step.* Buf, Go, dbt,
   Confluent. v2: the ecosystem installs a version; `meta deps sync` is the fetch step; the
   lock pins bytes (§2.3).
2. *The publisher marks the public surface, and the marker is enforced at resolution, not
   documented.* Smithy's `@private` changes both what may be referenced and what the diff
   counts; dbt's `access` is a parse error; projections and contracts *filter what is
   published*. This is the evidence #299 asked for, and it corrects the v0.3 memo's premise
   ("a marker would be a hint") in one respect only: enforcement is real when it happens at
   *publication*. v2 keeps the memo's conclusion that the marker is not a metamodel
   attribute and puts it where Smithy projections put it — in build config: `include` /
   `exclude` / `files` on the generator (§2.2). A node that is not exported is not in the
   artifact, so it cannot be referenced and cannot break anyone.
3. *Consumer extension comes in three shapes, in increasing risk.* Decorate-in-place
   (TypeSpec `@@`, Smithy `apply`) attaches attributes, never members; compose-new (Smithy
   mixins, LinkML `is_a` + monotonic `slot_usage`, TypeSpec `extends`, dbt `ref`) creates a
   consumer-owned node over the publisher's; true in-place augmentation (federation field
   contribution, Salesforce subscriber fields) exists only where ownership is hard-ruled
   (`@shareable` conflicts are composition errors; a namespace prefix). v2's `reference`
   mode is the first two shapes (overlay for attributes/presentation/validators — LinkML's
   monotonic narrowing is the same idea; `extends` for new nodes) and its `own` mode is the
   third, with `ERR_MERGE_CONFLICT` playing `@shareable`'s role (§2.4, §2.7).
4. *Breaking-change taxonomies split by audience and direction*: Buf's FILE/PACKAGE/WIRE,
   Confluent's reader-vs-writer, Smithy's severity ladder, dbt's columns/types/constraints.
   All four are **publisher-side** (old vs new, consumers invisible). Only TypeSpec's
   versioned-reference check, GraphOS operation checks and Salesforce's prohibition are
   **usage-aware**. v2's classifier (§2.6) is usage-aware by construction — it runs on the
   consumer's side over the consumer's footprint — which is the gap #300 named. The
   publisher-side report is the same classifier pointed at two versions (§9).

**Closest match to "the consumer overlays the publisher's object and the build fails when
upstream removes or renames the target": none exactly.** TypeSpec's `@@dec(Lib.Model.prop)`
and Smithy's `apply Foo$bar` are resolved references into the library, so a removed target
is an unresolved reference (inferred from the syntax; the exact diagnostics were not
confirmed). Salesforce gives the guarantee by forbidding removal. MetaObjects' own
`overlay: true` + `ERR_OVERLAY_NO_TARGET` is already closer to the target than any of the
ten; what none supplies is the cross-repo case — which is what the snapshot + lock + the
explicit-flag rule add.

### 2.11 Discipline checklist

- **ADR-0023 / registry.** Nothing registers vocabulary; the manifest, lock and config keys
  are tool files; selection is config. `expected-registry.json` and `METAMODEL_VERSION` do
  not move; `check-metamodel-version.mjs` sees no diff.
- **Constants.** `DEPS_DIR`, `LOCK_FILE`, `MANIFEST_FILE`, `ARTIFACT_SUFFIX`,
  `DEPENDENCY_SOURCE_ID_PREFIX`, transport keys, modes, the widening/additive tables and the
  error codes are named constants in sdk / metadata `errors.ts` / Python `errors.py` +
  `config/dependencies.py`.
- **`no-hardcoded-metadata-dir`.** No new code names `metaobjects/`; the snapshot lives under
  `.metaobjects/deps/` and is loaded by the lock's artifact path, never walked; the
  generator's `files` default is the collection's own files.
- **Never mutate loaded metadata.** The generator serializes selected nodes of a frozen tree;
  the classifier reads two documents; the validators are read-only passes.
- **Cross-package `instanceof` ban.** Node guards only.
- **Public-surface discipline.** `Collection` gains members (MINOR); `FileSource` gains an
  option (MINOR); sdk `package.ts` / `workspace.ts` exports are marked `@deprecated` with a
  2.0 removal note (no removal); nothing is removed from the 1.x surface.

```ts
const DependencyName = z.string().regex(/^[a-z0-9][a-z0-9._-]*$/);
const Mode = z.enum(["reference", "own"]).default("reference");
const DependencySpecSchema = z.union([
  z.object({ name: DependencyName, path: z.string().min(1), mode: Mode }).strict(),
  z.object({ name: DependencyName, npm: z.string().min(1), dir: z.string().min(1).optional(), mode: Mode }).strict(),
  z.object({ name: DependencyName, python: z.string().min(1), dir: z.string().min(1).optional(), mode: Mode }).strict(),
]);
ConfigSchema = ConfigSchema.extend({ dependencies: z.array(DependencySpecSchema).default([]) })
  .refine(uniqueNames);
```

### 3.4 The snapshot

`.metaobjects/deps/<name>/<artifact>` — the artifact bytes verbatim; `sync` empties the
directory first. Never walked; loaded by the lock's `artifact` path with source id
`dep:<name>/<artifact>`. `.metaobjects/.gitignore` gains `!deps/` and `!deps.lock.json`.

### 3.5 The artifact

A canonical-JSON `metadata.root` document with **no root `package`**, whose top-level
children each carry an explicit `package`, in raw (own-layer) form, `extends` preserved,
top-level nodes sorted by resolution key, attribute keys alphabetized (the canonical
serializer's existing contract). Loadable by every port's JSON loader as-is.

## 4. Algorithms

### 4.1 `meta deps sync [<name>…] [--dry-run] [--accept-breaking [<name>]]`

For each declared dependency (all, or the named subset), in name order:

1. **Resolve** the transport to a directory (§2.1). Failure → `ERR_DEPENDENCY_UNRESOLVED`
   (what was tried; for `python`, which interpreter answered).
2. **Read** `<dir>/metaobjects.pkg.json` (strict). Absent, invalid, `name ≠ spec.name`,
   artifact missing, `sha256(artifact) ≠ integrity` → `ERR_DEPENDENCY_MANIFEST_INVALID`.
3. **`metamodelVersion`** major ≠ `METAMODEL_VERSION` major →
   `ERR_DEPENDENCY_METAMODEL_INCOMPATIBLE`; minor greater → warning.
4. **Load the artifact standalone** with core providers, strict. Any error, or top-level
   resolution keys ≠ `manifest.nodes`, or packages ≠ `manifest.packages` →
   `ERR_DEPENDENCY_MANIFEST_INVALID` (a publisher who bypassed the generator is caught here).
5. **Collision:** `nodes` intersecting another entry's → `ERR_DEPENDENCY_NODE_COLLISION`.
6. **Classify** against the current snapshot (§2.6) when one exists: load the consumer model
   (current snapshot + own sources) to compute the footprint; diff old vs new artifact on it;
   BREAKING without `--accept-breaking` → `ERR_DEPENDENCY_BREAKING_CHANGE`, report, exit 1.
7. **Write** (unless `--dry-run`): empty `.metaobjects/deps/<name>/`, copy the artifact,
   update the lock entry (pruning names no longer declared), write the lock.
8. **Report** per dependency: `synced <name> <old>→<new> (N node(s), K breaking / M
   compatible change(s))` / `unchanged` / `would change: …`.

Then load the full collection once and run the boundary validator (§4.4), so a sync that
produces an unloadable model fails in the same command.

### 4.2 `resolveCollection` / `resolve_collection` — the extension

After the existing own-source resolution:

1. Read `dependencies` (absent → `[]` → a project without dependencies resolves
   byte-identically to today).
2. Read the lock; verify names match, each artifact exists and hashes as recorded
   (`ERR_DEPENDENCY_SNAPSHOT_STALE`), no `nodes` collision (`ERR_DEPENDENCY_NODE_COLLISION`).
3. Build `dependencies: ResolvedDependency[]` — `{ name, version, mode, packages, nodes,
   artifactPath }` — and `fileIds` (`artifactPath → dep:<name>/<artifact>`).
4. `files` = artifacts (name order) followed by own files; `ownFiles`; `foreignOwner`,
   `governs`.

`loadMemory` gains `fileIds`; it builds `new FileSource(p, { id })`. Every routed command
passes `collection.files` and `collection.fileIds` through one helper
(`collectionLoadOptions(collection)`). Python's `_load_root_from_paths` builds
`FileSource(path, id=…)` and calls `loader.load(sources)` directly.

### 4.3 `sharedModelFile()` — the publisher generator

Inputs: `name`, `version?`, `files?` (default: `ctx.sourceFiles`, the collection's own files
— a new `GenContext` field the runner fills), `include`, `exclude?`. Runs once per run
(`oncePerRun`).

1. Standalone load of `files` with `ctx.registry` (new `GenContext` field: the run's
   composed registry), strict. Errors → generator error.
2. Select top-level nodes: `type ∉ {requirement, template}` and `matchesScope(fqn,
   compile({ include, exclude }))`. Empty selection → error.
3. Closure: for every selected node and each descendant, every `extends` target (object part
   of a dotted ref) and every `REF_BEARING_ATTR_NAMES` value's object part must be in the
   selection → else error listing `(referrer → target)` pairs.
4. Serialize: a `metadata.root` with no package; for each selected node (sorted by
   resolution key) `canonicalSerialize(node)` with an explicit `package` (the node's
   resolution-key package). Deterministic bytes.
5. Re-load the emitted string with **core providers**, strict → error names the offending
   attr/subtype ("the export needs provider X; Phase 1 exports must load with core
   vocabulary").
6. Emit `<name>.metaobjects.json` and `metaobjects.pkg.json` (§3.2; `integrity` over the
   artifact bytes; `version` per §2.2).

`compileScope` / `matchesScope` move from sdk to `@metaobjectsdev/metadata` (pure string
code, browser-safe) with sdk re-exporting them, so codegen-ts can use the grammar without
depending on sdk (the runner's comment already wishes for this).

### 4.4 `validateDependencyBoundary(root, collection)` — post-load, every command

For each top-level node `n` with `owner = foreignOwner(n.resolutionKey())`:

- `owner` defined and a local file contributed to `n` (its `source` is `merged` with a
  non-`dep:` contributor, or `n.source.files` has a non-`dep:` entry) and
  `n.resolutionKey() ∉ declaredOverlayKeys(ownSources)` → `ERR_DEPENDENCY_OVERLAY_IMPLICIT`.
- `owner.mode === "reference"` and a **local** contribution (a child whose parse-time
  `source.files` is non-`dep:`) is of type `field` / `identity` / `index` / `relationship` /
  `source`, or the node carries a locally-set `@table` / `@schema` / `@column` / `@kind`, or
  a local node is a TPH subtype whose discriminator base is foreign →
  `ERR_DEPENDENCY_SCHEMA_NOT_OWNED`.

Lives in `sdk/src/dependencies.ts` and `metaobjects/config/dependencies.py`; called right
after `loadMemory` / `_load_root*` by every loading command. Cross-port codes, per-port prose.

### 4.5 Selection composition

- **gen / verify --codegen (TS):** `scope: fqn => genCollection.inScope(fqn) &&
  genCollection.governs(fqn)`; explicit `meta gen <Foreign>` in `reference` mode → refused
  by name, exit 2; the runner's wording is unchanged and the CLI prefixes `N node(s) from
  dependencies not generated here: …`.
- **gen / verify --codegen (Python):** `run_gen(…, governs=collection.governs)`; `entities:`
  naming a `reference`-mode foreign node → exit 2.
- **migrate / verify --db (TS):** `governedPredicate(collection)` in
  `cli/src/lib/migrate-scope.ts` returns `{ predicate: fqn => governs(fqn) &&
  (inMigrateScope?.(fqn) ?? true), foreignNote }`; the three migrate pipelines and verify's
  schema gate call it. migrate-ts is unchanged (`scopeExpectedSchema` already takes the
  predicate and returns `outOfScope`).

### 4.6 `dependencyFootprint` and `classifyDependencyChanges` (§2.6)

`dependencyFootprint(root, collection) → Map<fqn, { owner, scope }>`: walk every
**local** top-level node (and descendants); collect targets from `extends`, `overlay`
membership (a local contribution to a foreign node), `REF_BEARING_ATTR_NAMES`, relationship
`@objectRef` / `@through`, `@implementedBy`, assigning the scope from the table in §2.6
(`whole` > `key` > `existence`; the widest wins); keep those with a foreign owner; close
`whole` entries over their `extends` chain.

`classifyDependencyChanges(oldDoc, newDoc, footprint) → Change[]`: for each entry, locate
the top-level node in both documents (by resolution key), restrict both to the scope, run the
node-keyed diff, map each leaf change through the table in §2.6. `Change = { fqn, path,
kind: "breaking" | "compatible" | "info", before, after, rule }`. Pure; corpus-asserted in
TS and Python.

## 9. Risks, and what is deliberately left out

**Risks**

- *The classifier's fail-closed tables will produce false BREAKINGs* on attributes nobody
  thought about. That is the design: the cost is one `--accept-breaking`, and every such
  event is a candidate table entry — the tables are named constants with a test per row.
- *`find_spec` imports the parent package* — the `python` transport runs the consumer's own
  environment at sync time only; `path` is the override.
- *A committed artifact can be hand-edited* — hash check at every load; `nodes` re-derived
  at sync; `verify --deps` compares to upstream.
- *Two publishers, one FQN* — `ERR_DEPENDENCY_NODE_COLLISION` at sync and load; the fix is
  a package rename upstream, which the classifier will then report as BREAKING to every
  consumer, correctly.
- *`own` mode against a shared database* — the mode a consumer takes when it instantiates a
  library model; taken by mistake against a model whose publisher owns the tables, `meta
  migrate` would propose the publisher's tables in the consumer's run. The out-of-scope
  note names every table by dependency in `reference` mode, and the doc states the rule the
  library's own downstream ADR states; a `--dry-run` shows it before anything is applied.
- *Public-surface changes* — `Collection` and `FileSource` gain members (MINOR); nothing is
  removed; the deprecations are JSDoc + CHANGELOG only.
- *Phase-2 ports before Phase 2* — Java/C# ignore unknown neutral keys today, so a consumer
  model referencing a foreign FQN fails there with `ERR_UNRESOLVED_OBJECT_REF` — loud, at the
  right place; the doc says which ports read `dependencies`.

**Left out (YAGNI), with the trigger that would bring each back**

- `git` transport — a consumer that cannot install through its ecosystem at all.
- `maven` / `nuget` transports and the JVM classpath read (`"commit": false`) — Phase 2,
  with the ports that consume them.
- Transitive dependencies (a manifest `dependencies` key) — a library of libraries; today an
  export must be closed, so the publisher exports the whole closure.
- `requires.providers` — an export needing non-core vocabulary; today refused at gen.
- Per-node `own: […]` inside a `reference` dependency — a consumer owning one table of a
  model it otherwise references; the library's downstream ADR says that should not exist.
- Folding `libraries` into `dependencies` (`{ "library": "ai", "mode": "own" }`) — the shape
  is exactly right; the migration is a separate, additive change once `own` mode has shipped.
- Publisher-side (usage-blind) breaking-change reports across versions — `buf breaking`'s
  shape; useful once a library has consumers it cannot see. The classifier already exists;
  it is a CLI verb away.
- `meta why <fqn>` (#306) — provenance is in place.
- Retiring the reserved `sources[].resource` / `sources[].package` arms — Phase 2, all four
  resolvers together.

## 10. Rulings (2026-09-11)

1. **Committed snapshot — confirmed**, with a local co-development override (D10 below). The
   legacy build-time classpath read stays a Phase-2 JVM option.
2. **Explicit `overlay: true` on every contribution to a foreign node — confirmed.** An upstream
   removal must fail the consumer loudly, never turn its amendment into a silent local object.
3. **Per-dependency `mode: reference | own` — confirmed.** A per-node override waits for a real
   case.
4. **The classifier tables start fail-closed as specified.** An entry moves to the widening or
   additive table when an `--accept-breaking` event shows the change was safe; each entry is a
   named constant with its own test.
5. **The exported surface is configuration, not design.** `sharedModelFile` selects by `files` /
   `include` / `exclude`, and a project may declare more than one `sharedModelFile` to publish
   several artifacts. A library starts with one artifact; the shipped skills must teach an agent
   to widen the selection or split artifacts without a design change.

### D10 — Local co-development override

When a library and a consumer change together, the consumer must be able to read the library's
working tree instead of its committed snapshot. The legacy loop was `mvn install` of a
`-SNAPSHOT` into the local repository; this is its equivalent.

- **`.metaobjects/deps.local.json`** maps a dependency name to a local path — the publisher's
  artifact output directory in a sibling checkout:
  `{ "<name>": { "path": "../library/<artifact-dir>" } }`. It is never committed: `meta init` and
  `meta deps sync` add it to `.gitignore`.
- **While an override is present, every load in every port reads the overridden artifact in
  place** instead of the snapshot, skips that dependency's snapshot hash check, and prints one
  warning per command naming the dependency and the path: "loading `<name>` from a local
  override, not the committed snapshot".
- **`meta deps sync <name>` copies from the override path** when one is active — the normal way
  to land a co-developed change: regenerate in the library, sync in the consumer, commit both.
- **`meta verify --deps` fails while any override is active**, so a green `verify --deps` always
  means the committed snapshot is what was checked. CI never has the file.
- **The publisher's artifact changes when the publisher runs `meta gen`** — its normal loop. The
  consumer never runs the publisher's generator.

Prior art: Go `replace`, Cargo `[patch]`, npm/pnpm `link`, Maven local-repository snapshots; the
stored survey's #301 (override without editing the lock).

## 11. Phase 1a scope (ruled 2026-09-11)

_A scope review after Task 5 asked whether v2 was over-built for the driving case. It was, in
the places this section names. The ruling — "B+", thin dependencies plus default exclusion of
imported metadata — supersedes the decisions marked below. Everything else in §§0–10 stands.
The plan (`docs/superpowers/plans/2026-09-11-fr-023-phase-1a.md`) is re-cut to match from Task 6._

### 11.1 What Phase 1a builds

1. **Thin dependencies.** `dependencies: [{ name, path }]` in `.metaobjects/config.json`
   (§3.1 minus `mode`); `meta deps sync` copies the publisher's generated artifact into the
   committed snapshot `.metaobjects/deps/<name>/` and writes `.metaobjects/deps.lock.json`
   (§3.3 minus `mode`: `version`, `metamodelVersion`, `resolvedFrom`, `artifact`,
   `integrity`, `packages`, `nodes`). Every port's collection resolver loads the snapshot
   files **first**, then the project's own files, and refuses to load when the snapshot does
   not match the lock (`ERR_DEPENDENCY_SNAPSHOT_STALE`), when two dependencies export one
   node (`ERR_DEPENDENCY_NODE_COLLISION`), or when a lock's `metamodelVersion` major differs
   from the toolchain's (`ERR_DEPENDENCY_METAMODEL_INCOMPATIBLE`). `meta deps check` and
   `meta verify --deps` compare the installed artifact's hash with the lock's and fail with
   `ERR_DEPENDENCY_UPSTREAM_DRIFT`. The publisher's artifact is generated by
   `sharedModelFile()` (§2.2, §4.3, TypeScript) — closure-checked, re-loaded with core
   providers, drift-gated by `verify --codegen`.

2. **Imported metadata is load-only by default.** A dependency's nodes are loaded so the
   consumer's model can *resolve* against them — reference by FQN, `extends`, `overlay: true`
   — and are **excluded from every action surface** unless the consumer's own scope names
   their package explicitly. In the maintainer's words: *no metadata is imported in runtime,
   code-generated from, or used on the `meta` CLI unless explicitly imported for that
   purpose.*

   The mechanism composes the two scope declarations that already exist with one rule
   built from the lock:

   - `imported(fqn)` — `packageOf(fqn)` is in the union of every lock entry's `packages`.
     A package the consumer's dependencies own; not a per-object list. (Ruled 2026-09-11 —
     see §11.5. The lock's `nodes` stays, for integrity, collision detection and the
     ownership refusal below, but it is NOT the exclusion key.)
   - **A consumer may not declare a new top-level node into a dependency's package.** Post
     load, a top-level object whose `packageOf(fqn)` is a dependency package and whose FQN
     is NOT in that dependency's `nodes` was declared locally into a package the consumer
     does not own: `ERR_DEPENDENCY_PACKAGE_NOT_OWNED`, naming the object, the package and
     the dependency, with the fix ("declare it in your own package and `extends` the
     dependency's node, or overlay the dependency's node with `overlay: true`"). An
     OVERLAY merges into the existing node, whose FQN *is* in `nodes`, so it passes
     untouched — only a genuinely new object is refused. This is what keeps a
     package-keyed rule from failing silently: without it, such an object would simply
     never generate, with no error and no output.
   - `explicitlyIncluded(pkg, patterns)` — some pattern in the list names `pkg` literally:
     split the pattern on `::`, drop the final (name) segment; the remaining segments contain
     no `*` and join to exactly `pkg`. `acme::common::**` and `acme::common::Address` name
     `acme::common`; `acme::**`, `**` and an absent list do not.
   - **Codegen and CLI** (`gen`, `verify --codegen`, the shared-enums artifact, the
     requirements ledger's denominator, and — through the option in §11.2 — the runtime):
     `inScope(fqn) = matchesScope(fqn, scope) && (!imported(fqn) ||
     explicitlyIncluded(packageOf(fqn), scope.include))`.
   - **Schema** (`migrate`, `verify --db`, offline generate, replay): `inMigrateScope(fqn) =
     (declaredMigrateScope?.(fqn) ?? true) && (!imported(fqn) ||
     explicitlyIncluded(packageOf(fqn), migrate.scope))`. The predicate is `undefined` — the
     byte-identical, untouched path — only when the project declares no `migrate.scope` **and**
     no dependencies. The suppression is **two-sided** through the seam `migrate.scope` already
     uses (`scopeExpectedSchema` → `outOfScope` → `unmanagedNames`), with one correction:
     an imported object the scope excludes is removed **before** `declaredSchemas` is
     computed. `scopeExpectedSchema` pins `diff`'s schema scope to the unscoped model on
     purpose ("a scope narrows objects, never schemas"), which is right for `migrate.scope` —
     the same model declared into that schema — and wrong for an import: the consumer never
     declared into the publisher's schema, so leaving it in scope would turn every table the
     publisher did *not* export into a `DROP` candidate. The refusal for a `migrate.scope`
     that matches nothing keeps reading the *declared* scope alone.
   - A shared enum is emitted for the entities that are selected: an abstract enum reaches
     `enums.ts` iff a selected entity's field resolves to it, decided by the using entity and
     never by the enum's own package (bindings are deferred, and a selected entity's generated
     file must compile).
   - `meta gen <Name>` / a Python target's `entities:` naming an excluded import is refused by
     name (exit 2) with the fix stated (`scope.include`), rather than silently generating
     nothing.

   **Explicit include replaces `mode`.** The legacy "consumer instantiates the shared model"
   case — the library's `own` mode — is: name the package in `scope.include` (generate it)
   and in `migrate.scope` (own its tables). Both are per-project declarations that already
   exist; nothing new is registered.

3. **Runtime scoping — DEFERRED (ruled 2026-09-11).** The maintainer's "runtime" meant
   *what metadata gets loaded*, which is item 2's collection resolver, not an
   `ObjectManager` predicate. Nobody asked for the `ObjectManager` option, so it is not
   built; the trigger to revisit is in §11.4. The original reasoning is kept below for
   whoever picks it up.

   ~~The runtime does not read `.metaobjects/config.json`, so it cannot
   know what is imported; the collection does. Each port's `ObjectManager` gains an optional
   predicate over the entity's fully-qualified name; an entity the predicate rejects is
   refused by name with a message that says it is loaded for resolution only. The documented
   idiom passes the collection's composed predicate:

   ```ts
   new ObjectManager({ metadata: root, driver, scope: collection.inScope })
   ```
   ```python

   ```
   Absent, the runtime behaves exactly as today (every loaded entity is addressable) — a
   default-open choice, because a runtime that silently hid entities from an app that never
   opted in would be a behaviour change for every existing consumer.~~

4. **Overlays.** No new loader rule. A consumer's amendment of a node it does not own must
   say `overlay: true` — that is what makes an upstream removal `ERR_OVERLAY_NO_TARGET`
   (raised by all four ports today) instead of a silent new object; the docs and the skills
   teach it. `meta verify` gains a TypeScript **authoring finding** (advisory, never fails a
   build, own cap, `--no-overlay-lint` / `META_NO_OVERLAY_LINT=1`): a top-level node declared
   in two or more files where more than one declaration lacks `overlay: true`. It fires while
   the base still exists, which is the only moment the missing flag can be caught. Verified:
   without the flag the TypeScript parser "silently reuse[s] existing or create[s] new" and the
   Python merge appends on a miss; with it, both fail loudly.

### 11.5 The exclusion key — evidence and ruling (2026-09-11)

The re-cut left one question open: is imported-ness keyed on the lock's `nodes` (per
object) or its `packages` (per package)? The design argued `nodes`, on one empirical claim
(§2.4): *"Declare new nodes in the dependency's package. Allowed; the legacy consumers
did."* The two keys differ in exactly one case — a consumer declaring a **brand-new**
top-level node into a dependency's package — so that claim was the whole argument. It was
checked.

| Evidence | Finding |
|---|---|
| The driving consumer | Declares exactly one package (its own). Zero overlays. Nothing in the publisher's package. `nodes` and `packages` are indistinguishable here. |
| The legacy Java estate, a shared framework package | Declared across **two** modules — the framework (publisher) and the app consuming it. So a consumer really does declare *into* a dependency's package. |
| …but which classes? | Publisher: `Base, Group, GroupType, Role, User, UserGroup, UserRole`. Consumer: `Group, GroupType, Role, User, UserGroup, UserRole`. **New in consumer: none.** The consumer amends via the data/ui/baseui overlay split. An amendment is an overlay — its FQN is in `nodes`, so both keys agree. |
| New nodes in a shared package elsewhere | Found — two classes declared in a `*.ui.xml` that its sibling `*.data.xml` does not declare — but **within one module**, the same owner's ui file adding to its own data file. No dependency boundary is crossed. |

**No instance in the estate distinguishes the two keys.** §2.4's claim is false as written.

**Ruled:** `packages` is the exclusion key — it is the maintainer's own model ("all metadata
loads into one big tree, then you include and exclude packages"), it is one concept rather
than two, and it needs no "ownership is per node, not per package" caveat. The one failure
mode a package-keyed rule introduces — a consumer node in a dependency package silently
never generating — is closed by making it a loud error
(`ERR_DEPENDENCY_PACKAGE_NOT_OWNED`) rather than a silent exclusion. `nodes` is retained in
the manifest and lock, where it still earns its place: `sync` verifies the artifact contains
exactly the nodes the manifest claims, two dependencies exporting one FQN collide, and the
refusal above needs it to tell an overlay from a new declaration.
