**Source review:** synthesized in the 2026-05-30 review (this session). "✓ verified" = confirmed by reading the code during planning; "reported" = from the review, not re-verified here.

### Task 0.2: `ExpressionParser` — stop lower-casing literals/NULL

**Files:** Modify `om/src/main/java/com/metaobjects/manager/exp/parser/ExpressionParser.java:48` (+ keyword handling); Test `om/.../exp/parser/ExpressionParserTest.java`.

Design: only `and`/`or` keyword matching is case-insensitive; field/operator/value tokens must preserve case. Simplest correct fix: remove the blanket `toLowerCase()` at the entry point and make the keyword comparisons (`ACTION_AND`/`ACTION_OR` detection) case-insensitive at their comparison sites instead.

- [ ] **Step 1 — failing tests:** (a) a quoted value `name = 'Test Me'` round-trips with original case in the resulting `Expression.getValue()`; (b) `field is null` (or the parser's NULL syntax) produces a null-valued `Expression` (today the `"NULL".equals(name)` sentinel can't match because the input was lowercased). Read the parser to confirm the exact NULL/operator syntax before writing assertions.
- [ ] **Step 2 — run, expect FAIL.**
- [ ] **Step 3 — fix:** drop `expressionString.toLowerCase()` from `parse(mc, …)`; make `and`/`or` detection use `equalsIgnoreCase` at the comparison points. Keep field-name lookups against `mc.hasMetaField(...)` exact (metadata names are case-preserving per WA1).
- [ ] **Step 4 — run, expect PASS;** `mvn -q -pl om test`.
- [ ] **Step 5 — commit:** `fix(om): ExpressionParser preserves literal/identifier case; case-insensitive only for and/or`

> **DESIGN FLAG:** if field-name matching was *relying* on lowercasing for case-insensitive metadata lookup, confirm against WA1 (case-preserving registry) — metadata names are case-sensitive, so exact match is correct. Verify no existing test asserts case-insensitive field names.

### Task 0.3: Guard the generic `getNextAutoId()` (racy + int-capped)

**Files:** Modify `omdb/.../driver/GenericSQLDriver.java:313-361`; Test in `integration-tests` (Derby) or a `GenericSQLDriver` unit test.

Decision (recommended, low-risk): **do not try to make MAX()+1 concurrency-safe** (you can't, portably). Instead (a) parse as `long` not `int` (fixes the silent `BIGINT` truncation), and (b) javadoc it loudly as a **single-writer / test-only fallback** — real dialects already override with sequences/identity. Optionally gate it behind a flag so production misconfig fails fast rather than silently colliding.

- [ ] **Step 1 — failing test:** with a `LongField` PK whose current MAX exceeds `Integer.MAX_VALUE`, `getNextAutoId` returns `max+1` without overflow. (Today `Integer.parseInt` throws / truncates.)
- [ ] **Step 2 — run, expect FAIL.**
- [ ] **Step 3 — fix:** `long i = Long.parseLong(tmp) + 1; return Long.toString(i);` + class/method javadoc: "Generic fallback only — not concurrency-safe; production dialects override with sequences/identity."
- [ ] **Step 4 — run, expect PASS;** `mvn -q -pl omdb,integration-tests test` (integration only if Testcontainers available; else omdb).
- [ ] **Step 5 — commit:** `fix(omdb): generic getNextAutoId uses long; document single-writer-only fallback`

## Tier 1 — Production-correctness gaps

### Task 1.1: Wrap migration `apply()` in a transaction

**Files:** Modify `migrate/SchemaMigrationEngine.java:50-57`.

Approach: the project already has an `inTransaction` template (FR-003 Plan 4). For DDL, wrap the change loop so a mid-failure rolls back (on dialects with transactional DDL — Postgres yes, Derby per-statement). Set `autoCommit=false`, execute all, `commit()`; on exception `rollback()` and rethrow; restore prior autoCommit in `finally`. Do NOT swallow.

- [ ] **Step 1 — failing test:** feed `apply()` a change list whose 2nd statement is invalid DDL against Testcontainers Postgres; assert the 1st change's effect is rolled back (table/column absent) and the original exception propagates. (Postgres has transactional DDL — the right place to assert this.)
- [ ] **Step 2 — run, expect FAIL** (today statement 1 commits).
- [ ] **Step 3 — implement** the autocommit-off / commit / rollback wrapper around the `for (Change ch : d.changes())` loop.
- [ ] **Step 4 — run, expect PASS;** confirm Derby migration tests still green (Derby commits per-statement — document that atomicity is Postgres-grade, best-effort on Derby).
- [ ] **Step 5 — commit:** `fix(omdb-migrate): apply() runs all DDL in one transaction (rollback on failure)`

### Task 1.3: Introspect indexes, FKs, and views (idempotency)

### Task 1.4: MSSQL + Oracle paging

**Files:** `driver/MSSQLDriver.java`, `driver/OracleDriver.java`, `GenericSQLDriver.java:1505` (the commented `getSelectStatementWhere` TOP/subquery hook).

> **DESIGN FLAG:** modern SQL Server (2012+) and Oracle (12c+) both support `OFFSET … FETCH NEXT … ROWS ONLY` — far simpler than the legacy `TOP`/`ROWNUM` subquery dance. Recommend implementing standard `OFFSET/FETCH` for both (requires `ORDER BY`, which paged queries should have) rather than resurrecting the commented subquery code. Confirm minimum supported server versions with the user.

- [ ] **Step 1 — failing tests:** `getSelectStatementWhere` (or `readMany`) with a limit/offset on the MSSQL and Oracle drivers produces SQL that actually bounds the result; assert the generated SQL contains `OFFSET … FETCH NEXT …` and that Oracle's clause is not appended after `ORDER BY` as malformed text. (Driver-level SQL-string assertions; live DB optional since CI lacks MSSQL/Oracle containers.)
- [ ] **Step 2 — run, expect FAIL.**
- [ ] **Step 3 — implement** `OFFSET ? ROWS FETCH NEXT ? ROWS ONLY` in both drivers' range handling; delete the stale commented `TOP`/`ROWNUM` code.
- [ ] **Step 4 — run, expect PASS.**
- [ ] **Step 5 — commit:** `fix(omdb): standard OFFSET/FETCH paging for MSSQL + Oracle`

## Tier 2 — Hygiene & robustness

### Task 2.1: Unify identifier quoting behind a validating helper

`GenericSQLDriver` ships an identity `quoteIdent`; only Postgres overrides. Push a validating default down (strict identifier-pattern check + dialect quote char) and route ALL DDL identifier emission (`createTable`/`createIndex`/`createForeignKey`/`createSequence`) through it instead of raw `append(name)`. Model on the existing `PostgresDriver.q()`. Test: a column named with a reserved word / mixed case emits quoted DDL on each dialect; an identifier containing the quote char is rejected. Commit per dialect or as one.

### Task 2.2: Make the DB validator fail when it should

`validator/MetaClassDBValidatorService.java:182` swallows all exceptions (empty catch), making `TableDoesNotExistException` unreachable. Restore propagation when `autoCreate=false` (test: missing table → throws). Reconcile the commented-out `init()` error handling.

### Task 2.3: Dead-code purge

Delete the large commented-out blocks: `ObjectManagerDB` (~40%: OQL/key-parsing, `getFieldForColumn` cache), `GenericSQLDriver` (~600 lines incl. `getDeleteStatement` dead body, `getSelectStatementForRef/Object`), the unused `DirtyWriteException` factory surface (or wire it into `updateObject`/`deleteObject` so the structured context is actually used — pick one), and the `ExpressionParser.main()` method. No behavior change; full suite green before/after. Commit in reviewable chunks per file.

### Task 2.4: Legacy-idiom cleanup (opportunistic)

`Class.newInstance()` → `getDeclaredConstructor().newInstance()`; `Expression` int-constants → enum (with bounds safety); `throws Exception` → narrower; `if(x!=null)return true;else return false` → `return x != null`; log string-concat → SLF4J `{}`; `getPreparedStatement` unknown-type `toString()` coercion → explicit `setObject`. Low-risk, do where touched; not a blocker.

### Task 2.5: Tier 2 gate + final

- [ ] Full Java reactor `mvn -q test` green. Cross-cutting code-reviewer + code-simplifier. Finish branch (merge forward + push) via finishing-a-development-branch.

## Sequencing & cut-line guidance

- **Ship Tier 0 first** — it's a few hours, all verified, all trust-affecting, low-risk. Could merge as its own PR.
- **Tier 1 is the real work.** Items 1.3 (introspection) and 1.4 (paging) are the largest and each carry a design decision (introspection cut-line; OFFSET/FETCH min-versions) — resolve those with the user before implementing. 1.1/1.2/1.5/1.6 are contained.
- **Tier 2 is optional polish** — do 2.1 (quoting) and 2.2 (validator) if security/robustness matters; 2.3/2.4 are quality-of-life.
- **Out of scope:** the god-class decomposition of `ObjectManagerDB`/`GenericSQLDriver` (architectural; not a bug). The `getPreparedStatement` "NPE" (review false positive — do not touch beyond the toString nit in 2.4).
